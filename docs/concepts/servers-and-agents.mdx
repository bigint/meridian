A server in Meridian is one machine. Two sources name it, and they rarely use the same name:

- **Git** names it by the host that Kamal connects to over SSH, such as `web-1.internal.example.com` or `10.0.0.5`.
- **The agent** names it by its machine id, `/etc/machine-id`, and reports the machine's own hostname, such as `web-1`.

Meridian joins the two into one server row. This page explains how.

## Placeholder servers from Git

When a sync finds a host in a config's `servers`, Meridian looks for a server with that host. It creates one when none exists, named after the host. This placeholder has no machine id and has never reported, so every app that Git assigns to it shows as **unknown** on the board.

Before it creates a placeholder, Meridian checks whether an agent already reported from that machine under another name. A server made by an agent, with no apps assigned yet, is taken over when the first DNS label of its name matches the host's and exactly one such server exists. Meridian then renames it to Git's host.

## Identity is the machine id

A server's identity is the machine id that its agent sends. The agent reads it from `/host/etc/machine-id`, the host's file mounted into the container, then from `/etc/machine-id`. `MERIDIAN_MACHINE_ID` overrides both. The agent refuses to start without one.

The hostname comes from `MERIDIAN_HOSTNAME`, then `/host/etc/hostname`, then the container's own hostname. It must be a DNS name or an IP address.

## How an agent claims a server

The first snapshot from a new machine id finds its server in this order:

<Steps>
  <Step title="The token's server">
    A per-server token is bound to the first server it reported for, and its snapshots land there.
  </Step>
  <Step title="A server with the same machine id">
    The machine has reported before, perhaps with another token.
  </Step>
  <Step title="An unclaimed server whose host is the reported hostname">
    Unclaimed means no agent has reported for it yet. The server's hostname or name must equal the reported hostname exactly.
  </Step>
  <Step title="A silent server that Git places at the reported hostname">
    Its old agent has been silent for 10 minutes, so the machine was rebuilt. See [a rebuilt machine](#a-rebuilt-machine).
  </Step>
  <Step title="An unclaimed server with the same first DNS label">
    The agent reports `web-1`, and Git says `web-1.internal.example.com`. This counts only when exactly one unclaimed server matches, and never for IP addresses.
  </Step>
  <Step title="A new server">
    Named after the reported hostname. Git may claim it later, as described in [placeholder servers](#placeholder-servers-from-git).
  </Step>
</Steps>

| Git's host | The agent reports | Result |
| --- | --- | --- |
| `web-1.internal.example.com` | `web-1.internal.example.com` | Claimed, exact match |
| `web-1.internal.example.com` | `web-1` | Claimed, first label |
| `web-1.eu.example.com` and `web-1.us.example.com` | `web-1` | A new server, because two match |
| `10.0.0.5` | `web-1` | A new server. Set `MERIDIAN_HOSTNAME=10.0.0.5`. |

<Tip>
If your configs list servers by IP address, set `MERIDIAN_HOSTNAME` on each agent to the address Kamal uses. Meridian never matches an IP address by its first label.
</Tip>

### A rebuilt machine

A rebuilt machine gets a new machine id. Meridian hands it the old server when three things hold:

- Git places the server.
- The server's hostname or name is exactly the hostname the new agent reports. A first DNS label is not enough.
- The old agent has been silent for 10 minutes, or for its stale limit when that is longer.

Until then, a new machine on a fleet token reports as a server of its own, and Git's server shows as stale. Once the old agent has been silent long enough, the next snapshot moves the new machine onto Git's server and deletes its own. A per-server token bound to the old server works the same way. It gets a `422` while the old server could still be alive, then takes it over.

A shorter silence, or a server that Git doesn't place, is never taken over, so two live machines can't swap identities.

## Tokens

Every agent needs a token, which an admin creates on the [Agents](/guides/agent) page. Meridian stores only its SHA-256 digest.

| Token | Identity | Revoke it, and |
| --- | --- | --- |
| Per-server | Bound to the first server that reports with it. Another machine using it gets a `422`, unless that server has been silent for 10 minutes. | Only that server stops reporting. |
| Fleet, shared by many servers | Each snapshot's machine id. | Every server that uses it stops reporting. |

A per-server token is safer, because a leaked token reports for one machine only. A fleet token is easier to roll out to many servers through one Kamal config. Each token may send 120 snapshots a minute. For a fleet token, the limit counts each machine separately, with a ceiling of 12,000 a minute for the whole token.

## Labels

An agent sends labels from `MERIDIAN_LABELS`, a comma-separated list of `key=value` pairs:

```yaml config/deploy.yml
accessories:
  meridian_agent:
    env:
      clear:
        MERIDIAN_LABELS: region=sgp,provider=hetzner,role=web,city=Singapore
```

Labels come only from the agent. Each snapshot replaces the server's labels, so a label removed from `MERIDIAN_LABELS` goes at the next snapshot. Meridian keeps up to 32 labels, with keys up to 64 characters and values up to 128.

A few keys mean something to Meridian:

| Label | Used for |
| --- | --- |
| `region` | A board filter and grouping. The board groups by region on its own above 30 servers, or when servers use more than one region. Live board updates go out per region. |
| `provider` | A board and map filter, and grouping. |
| `role` | A board and map filter, and grouping. It is a label of the machine, not Kamal's role. |
| `city` | The place name on the map. Without it, the most common `region` names the place. |
| `lat`, `lng` | The server's position on the map. `latitude`, `longitude` and `lon` also work. |

Any other label shows on the server's page. **New app** accepts a label selector such as `role=web,region=sgp` to pick every matching server.

An admin can also set a server's position with **Save location** on its page. A position in the agent's labels replaces it at the next snapshot.

## What an agent reports

Each snapshot holds the machine id, hostname, agent version, interval and labels, and one entry per container that Kamal started:

- the container's name, image, service, role and destination labels,
- its version, read from the container name the way Kamal does,
- its state, health and start time,
- its kind: an app, an accessory, or `kamal-proxy`.

Nothing else leaves the server in a snapshot. Environment variables, commands and mounts are never sent. Live stats, logs and traffic travel separately, and only while someone watches. See [Agent protocol](/reference/agent-protocol).

## Quiet agents

Meridian calls a server stale when its agent has been silent for three of its intervals, and never less than 45 seconds. [Drift](/concepts/drift#stale-timing) has the details. The **Silent agents** list on the Agents page shows every quiet server, followed by the servers that no agent has ever reported from. On the Servers page, **Only silent agents** filters to the quiet ones.
