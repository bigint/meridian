The **Secrets** page lists the secret names your [Kamal](/reference/glossary#kamal) configs use, such as `DATABASE_URL`. You can set or change each value there. The value goes straight to your [infra repository](/reference/glossary#infra-repository)'s encrypted GitHub Actions secrets. Meridian never stores, logs or shows it, and can't read it back.

## Set or rotate a value

<Steps>
  <Step title="Open Secrets">
    Open **Secrets** under **Manage**. Each project has its own table.
  </Step>
  <Step title="Type the value">
    In the name's row, type the value in the **Set or rotate** column. The field hides what you type.
  </Step>
  <Step title="Save it">
    Click **Set**, or **Rotate** for a name that was set before. Meridian says `DATABASE_URL set. Redeploy the apps that use it to pick it up.`
  </Step>
  <Step title="Redeploy">
    Running containers keep the old value until Kamal restarts them. Open each app in **Used by** and click **Redeploy**. See [Redeploy the current version](/guides/deploy#redeploy-the-current-version).
  </Step>
</Steps>

**Last set** shows when the value was last set through Meridian. [Activity](/guides/activity) records who set it, as `secret.set`. A value set on GitHub directly shows `not set through Meridian`. Meridian can't tell whether GitHub has it.

<Accordion title="How the value travels">
  Meridian asks GitHub for the repository's Actions public key. It seals the value with that key (a libsodium sealed box) and sends GitHub the sealed value. Only GitHub can open it. Meridian keeps the time and who set it, never the value. The value isn't saved to the database, written to a log, put on a job queue, or sent to other pages.
</Accordion>

## Where the names come from

On every sync, Meridian lists the secret names in each config. It reads these keys:

- `env.secret`, at the top level, under each role in `servers`, and under each accessory.
- `env.tags.<tag>.secret`, for env set per server tag.
- `registry.password`, when it is a list of names.

This config gives three names. **Used by** shows the apps that use each one.

```yaml config/deploy.yml
env:
  secret:
    - DATABASE_URL
    - RAILS_MASTER_KEY
registry:
  server: ghcr.io
  username: acme
  password:
    - KAMAL_REGISTRY_PASSWORD
```

<Accordion title="Edge cases">
  - An aliased name, `KEY:SECRET`, lists the second part. `TUNNEL_TOKEN:CLOUDFLARE_TUNNEL_TOKEN` lists `CLOUDFLARE_TUNNEL_TOKEN`, the name the value is stored under.
  - Meridian never reads `.kamal/secrets` or any other secrets file.
  - Names GitHub can't store, such as one that starts with `GITHUB_`, are left out. They don't stop the sync.
  - A name that sync found and nobody set goes away once no config uses it. A name set through Meridian, or added by hand, stays, marked `not referenced by any config`.
</Accordion>

## Add a name by hand

Add a name before any config uses it, or one that only CI reads.

<Steps>
  <Step title="Open the form">
    Under the project's table, open **Add another name**.
  </Step>
  <Step title="Fill it in">
    Type the **Name**, such as `DATABASE_URL`. Meridian turns it into upper case. It holds only letters, digits and `_`. It must not start with a digit or `GITHUB_`, and has at most 128 characters. **Value (optional)** sets it in the same step.
  </Step>
  <Step title="Add it">
    Click **Add**.
  </Step>
</Steps>

Adding and setting allow 20 requests a minute from one IP address.

## How Kamal gets the values

The [CI workflow](/reference/glossary#ci-workflow) turns every repository secret into an environment variable before it runs Kamal. Kamal's secrets files then map each name to its variable:

```bash .kamal/secrets
KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD
RAILS_MASTER_KEY=$RAILS_MASTER_KEY
DATABASE_URL=$DATABASE_URL
```

Kamal always reads `.kamal/secrets-common`. It also reads `.kamal/secrets` for a config without a destination, or `.kamal/secrets.<destination>` for one with a destination, such as `.kamal/secrets.production`. A name missing from those files fails the run with `Secret 'DATABASE_URL' not found in ...`.

## The two CI secrets

The workflow itself needs two repository secrets, whatever your configs say. Set both before the first deploy.

| Secret | What it is |
| --- | --- |
| `KAMAL_SSH_PRIVATE_KEY` | The private key CI uses to SSH to your servers. Its public key must be in each server's `authorized_keys` for the user Kamal connects as. |
| `KAMAL_REGISTRY_PASSWORD` | The password or token Kamal logs in to the registry with. The configs Meridian writes name it in `registry.password`. |

`KAMAL_REGISTRY_PASSWORD` shows on the Secrets page once a config uses it. `KAMAL_SSH_PRIVATE_KEY` shows only after you add it with **Add another name**. You can also set it on GitHub directly. See [CI workflow](/reference/ci-workflow).
