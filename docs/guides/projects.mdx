A [project](/reference/glossary#project) is one [infra repository](/reference/glossary#infra-repository) added to Meridian. That is the Git repository that holds your Kamal configs. Add one, and the board shows every app in it.

Meridian reads the configs, and commits deploys, rollbacks and new apps back to the repository. It changes nothing else there.

## Before you start

- GitHub access: the GitHub App installed on the repository, or a token. See [Install](/install) and [GitHub App](/reference/github-app).

## Add a project

<Steps>
  <Step title="Open the form">
    Open **Projects** under **Manage**, and click **Add project**.
  </Step>
  <Step title="Fill it in">
    - **Name**: what Meridian calls the project, such as `Infra`.
    - **Repository**: the GitHub repository, as `owner/name`, such as `acme/infra`. Each repository can be one project only, and case doesn't matter.
    - **Branch**: the branch Meridian reads and commits to, `main` by default.
    - **GitHub App installation ID**: the number at the end of the URL after you install the App. Leave it blank if Meridian uses a token.
    - **Config paths**: which files are Kamal configs. See [Choose config paths](#choose-config-paths).
    - **Commit changes directly instead of opening pull requests**: see [Direct commits](#direct-commits).
  </Step>
  <Step title="Save">
    Click **Create Project**. Meridian says `Project added. Syncing now.` and reads the repository in the background.
  </Step>
  <Step title="Check what it found">
    The project's page lists **Configs found**, with each app's config, destination, server count and hostnames. **Parse errors** lists any config Kamal couldn't read.
  </Step>
</Steps>

Next, add the CI workflow, so deploys can run.

## Add the CI workflow

Meridian never runs Kamal. The [CI workflow](/reference/glossary#ci-workflow), `.github/workflows/meridian-deploy.yml`, does that in GitHub Actions.

<Steps>
  <Step title="Add the two secrets">
    Add `KAMAL_SSH_PRIVATE_KEY` and `KAMAL_REGISTRY_PASSWORD` to the repository, plus any secrets your configs use. See [Secrets](/guides/secrets#the-two-ci-secrets).
  </Step>
  <Step title="Propose the workflow">
    On the project's page, click **Add CI workflow** and confirm. Meridian opens a pull request titled `ci: deploy with Kamal when a version file changes`. If the project allows direct commits, it commits the file instead.
  </Step>
  <Step title="Merge it">
    Review and merge the pull request. Deploys work from then on.
  </Step>
</Steps>

The workflow runs `kamal deploy` when a push changes a `.version` file. Meridian also starts it for a redeploy.

You can edit the workflow, but keep its `run-name`, because Meridian finds redeploy runs by it. If GitHub's runners can't reach your servers, set the repository variable `MERIDIAN_RUNS_ON` to your own runner, such as `self-hosted`. See [CI workflow](/reference/ci-workflow).

## Choose config paths

**Config paths** are patterns, separated by commas, that say which files in the repository are Kamal configs. The default, `config/deploy*.yml`, is Kamal's own layout.

- `*` matches within one folder.
- `**/` matches any number of folders, including none.
- `{a,b}` matches either word.
- Only files ending in `.yml` or `.yaml` count.

A file whose name ends in `.<destination>.yml` is a [destination](/reference/glossary#destination) of the config beside it, as in Kamal. With the default pattern:

<Tree>
  <Tree.Folder name="config" defaultOpen>
    <Tree.File name="deploy.yml" />
    <Tree.File name="deploy.staging.yml" />
    <Tree.File name="deploy.production.yml" />
    <Tree.File name="deploy.version" />
    <Tree.File name="deploy-blog.yml" />
  </Tree.Folder>
</Tree>

That is two configs and three [apps](/reference/glossary#app). `config/deploy.yml` has the destinations `staging` and `production`, so it is two apps. `config/deploy-blog.yml` has none, so it is one app.

To keep one file per app in a folder, use `deploy/*.yml`. **New app** puts each new config at the first pattern with a single `*`, with the service name in its place. See [Where the config goes](/guides/new-app#where-the-config-goes).

<Accordion title="Edge cases">
  A file such as `config/deploy.staging.yml` is a destination only when `config/deploy.yml` or `config/deploy.yaml` exists.
</Accordion>

The full layout, with version files, is in [Infra repository](/reference/infra-repository).

## Direct commits

By default, Meridian proposes new apps, the CI workflow and tunnel connector changes as pull requests. Each goes on a branch named `meridian/<what>-<6 hex digits>`, such as `meridian/new-shop-3fa9c1`.

Tick **Commit changes directly instead of opening pull requests**, and your change goes straight to the branch. The project's page then says **Direct commits** under **Changes**. Activity records a direct commit as `project.committed`, and a pull request as `project.pull_request`.

Deploys and rollbacks always commit straight to the branch, whatever this setting says. They change only version files.

## Sync

Meridian reads a project again:

- On every push to the branch, when GitHub sends the push [webhook](/reference/glossary#webhook).
- Every 30 seconds, with or without webhooks. If nothing changed, this costs no GitHub rate limit.
- When you click **Sync now**, even if the branch hasn't moved. Meridian says `Syncing acme/infra.`
- When you save a new repository, branch, installation ID or config paths.

Each sync reads only the files that changed, and parses the configs with Kamal. The project's page shows **Synced**, with the commit and the time.

An app whose config is gone from Git leaves the board. An app whose config fails to parse stays, with its deploys and releases, until it parses again.

## Fix parse errors

When Kamal can't read a config, the project's page lists it under **Parse errors**, and **Projects** shows a badge such as `✕ 2 parse errors`. Each error has the file and line, a **view** link, and Kamal's message:

```text
config/deploy.staging.yml:14
proxy: unknown key: hots
```

<Steps>
  <Step title="Open the line">
    Click **view** to open the file at that line, at the commit Meridian last read.
  </Step>
  <Step title="Fix it in Git">
    Fix the config and push to the branch. When the error is in a destination file, the line points there.
  </Step>
  <Step title="Check it cleared">
    The next sync parses it again. **Parse errors** then says `No parse errors`, with the Kamal version it used.
  </Step>
</Steps>

<Accordion title="When the parser hangs or crashes">
  Then nothing in that sync parses. Meridian keeps every app as it was and shows one error without a file. Look at the configs the last push changed.

  Meridian tries that commit again after 1 minute, then waits twice as long each time: 2, 4, 8 minutes, up to once an hour. It reads a new push at once.
</Accordion>

## Edit or remove a project

Click **Edit** on the project's page to change any field. Click **Update Project** to save.

To remove a project, click **Remove project** on its **Edit** page and confirm. Meridian forgets the project and its apps, releases, deploys and secret names. It says `Project removed. Nothing in Git was changed.` Nothing on your servers changes either.
