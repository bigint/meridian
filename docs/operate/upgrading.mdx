title: "Upgrading"
description: "Move Meridian to a new release with Kamal, check it, and go back if you need to."

---

To upgrade, you deploy Meridian's new image with Kamal, as you deployed the first one. Each release publishes the app and agent images, tagged with the release and with `latest`:

- `ghcr.io/bigint/meridian:<tag>`, the app.
- `ghcr.io/bigint/meridian-agent:<tag>`, the agent.

Pin a tag, such as `v0.1.5`, not `latest`. Then you choose when to upgrade.

## Before you upgrade

1. Read the release's entry in the [changelog](/changelog). If the release needs an extra step, its **Upgrading** section lists it. For example, press **Add CI workflow** again, or change the agent accessory.
2. Back up the database, or check that Litestream is current. See [Backups](/operate/backups).

## Upgrade Meridian

From your copy of Meridian's `config/deploy.yml`, deploy the new tag:

<Tabs>
  <Tab title="Published image">
    ```bash
    kamal deploy --skip-push --version v0.2.0
    ```

    `--skip-push` tells Kamal not to build. Each server pulls `ghcr.io/bigint/meridian:v0.2.0` instead.
  </Tab>
  <Tab title="Your own build">
    Check out the release. Kamal builds it and pushes it to your registry, the `image:` in `config/deploy.yml`:

    ```bash
    git checkout v0.2.0
    kamal deploy
    ```
  </Tab>
</Tabs>

Kamal starts the new container beside the old one. Once `/up` answers, [kamal-proxy](/reference/glossary#kamal-proxy) sends traffic to the new container, and Kamal stops the old one. You and the agents see no downtime.

### What runs on boot

Before the server starts, `bin/docker-entrypoint` runs `bin/rails db:prepare`. It creates any missing database and runs new migrations on all four databases: primary, cache, queue and cable. Then Thruster starts on port 80, in front of Puma.

The migrations run while the old container still serves. A `job` role that runs `bin/jobs` doesn't run `db:prepare`. So deploy `web` first, or deploy both together with `kamal deploy`.

### The database

The SQLite files live in the `meridian_storage` volume, mounted at `/rails/storage`. The volume outlives every container, so a deploy keeps all data. Don't remove the volume. To move Meridian to another host, copy the volume too.

### Check it

```bash
curl -fsS https://meridian.example.com/up
kamal logs
```

`/up` answers when Meridian is up. **Settings → Connections** shows the Kamal version the new release parses configs with.

## Go back

Kamal keeps the last five app containers on the host, stopped. `kamal rollback` starts one of them again. To return to the previous release:

```bash
kamal rollback v0.1.5
```

`kamal rollback` doesn't undo migrations. If the older release can't read the migrated database, restore the backup you took before the upgrade.

## Upgrade agents

The agent runs as a Kamal accessory in an infra repository's config, so you upgrade it there. Change its image tag, then run `kamal accessory reboot meridian_agent`. See [Upgrade the agent](/guides/agent#upgrade-the-agent).

## Update the CI workflow

The [CI workflow](/reference/glossary#ci-workflow) is a file in each infra repository, so a Meridian upgrade doesn't change it. When a release changes the workflow's template, press **Add CI workflow** on each project's page again. Then merge the pull request. See [CI workflow](/reference/ci-workflow).
