Meridian changes your servers only through Git and your CI. This page says what it can reach, what it stores, and the steps that keep it safe.

## What Meridian can and can't do

Meridian **can**:

- Commit to your [infra repository](/reference/glossary#infra-repository) and open pull requests there, through its GitHub App.
- Set the repository's GitHub Actions secrets.
- Start the [CI workflow](/reference/glossary#ci-workflow), which runs [Kamal](/reference/glossary#kamal) against your servers.
- Read what the [agents](/reference/glossary#agent) report about each server's Kamal containers.

Meridian **can't**:

- Connect to a server. It has no SSH keys, and agents connect out to it.
- Run Kamal itself.
- Read a secret's value back from GitHub.
- Start, stop or change a container through an agent. Agents only read.

Your CI runs whatever the infra repository says. So anyone who controls Meridian can deploy anything to your servers. Treat Meridian like your CI system.

Meridian adds a second way to change the infra repository, but no new power. Anyone with write access to that repository can already deploy, with or without Meridian.

## What Meridian keeps

| Asset | Where it lives | Who can read it |
| --- | --- | --- |
| GitHub App private key | `GITHUB_APP_PRIVATE_KEY`, in the container's environment | The Meridian process |
| GitHub installation tokens | Process memory, for up to one hour | The Meridian process |
| Agent tokens | SHA-256 digests in SQLite. The token is shown once, when it is created. | Nobody |
| Secret values | GitHub only, sealed with the repository's public key | Nobody. Meridian can't read them back. |
| Passwords | bcrypt digests in SQLite | Nobody |
| Sessions | A signed, permanent, `HttpOnly`, `SameSite=Lax` cookie, `Secure` over HTTPS | The browser |
| Live stats, logs and traffic | Nowhere. Relayed to the open page. | You, while the page is open |

Git holds your configs and their history. Meridian's database holds your account, agent tokens, the activity trail and what agents last reported.

## Run it safely

<Steps>
  <Step title="Keep it on a private network">
    Run Meridian on a VPN, a tailnet or behind an internal load balancer. Agents need to reach it. GitHub doesn't: Meridian polls it. You don't need to reach it from the public internet.
  </Step>
  <Step title="If it must be public, use HTTPS">
    Keep `MERIDIAN_URL` on `https://`. Meridian then forces HTTPS, sends HSTS, marks cookies `Secure`, and answers only to that URL's host. Set a long random `SECRET_KEY_BASE`.
  </Step>
  <Step title="Give GitHub the least access">
    Install the App only on the infra repository. Use the App, not a personal access token, which reaches every repository its owner can. See [GitHub App](/reference/github-app).
  </Step>
  <Step title="Give servers the least access">
    Run the agent behind the Docker socket proxy, both on their own `meridian` network, as the template does. Never put the proxy on Kamal's `kamal` network, and never publish its port. Anything that reaches port 2375 can read every container's environment variables, files and logs. See [Install the agent](/guides/agent).
  </Step>
  <Step title="Back up the database">
    Losing it loses the activity trail, your account and agent tokens. Git keeps everything else. See [Backups](/operate/backups).
  </Step>
</Steps>

## How each protection works

<AccordionGroup>
  <Accordion title="It never connects to servers">
    Agents connect out to Meridian. Meridian has no SSH keys and opens no connection to a server. Live stats, logs and traffic travel over a WebSocket that the agent opens to `/cable`. Meridian uses it only to say "someone is watching, send for 30 seconds".
  </Accordion>
  <Accordion title="It never runs Kamal">
    CI runs Kamal, from the repository, where every change is a commit or a reviewed pull request. Meridian commits version files and starts the workflow.
  </Accordion>
  <Accordion title="Secret values are write-only">
    Meridian seals a value in the request that receives it, sends it to GitHub, and drops it. The value is filtered from logs, never stored on a model, never passed to a job and never broadcast. Tests check all of this with a known marker value.
  </Accordion>
  <Accordion title="Configs are parsed apart from Meridian">
    ERB in a Kamal config is Ruby code from your infra repository. `bin/kamal-parse` runs it in a separate process with an empty environment. That process works in a temporary folder that holds only the files fetched from Git, so it can't read Meridian's keys or memory. Meridian kills a parse that runs over 60 seconds, and refuses a path that points outside the folder.

    `bin/kamal-parse` strips the environment, but it is not a sandbox. So Meridian checks everything it writes into a Kamal config against a strict format first. That covers hosts from a URL, form fields, and host names that agents report. A host name can hold only letters, digits, `.`, `_`, `:` and `-`, so it can't carry ERB or YAML.
  </Accordion>
  <Accordion title="Agents are read-only and narrow">
    The agent calls only list, inspect, stats and, with logs on, logs. It never sends environment variables, commands, entrypoints or mounts. It never sends Docker calls through an HTTP proxy. Live stats are numbers only.

    The socket proxy allows every read under `/containers`, so only the agent shares its network. See [Agent protocol](/reference/agent-protocol#what-the-agent-never-sends).
  </Accordion>
  <Accordion title="Logs are opt-in and never stored">
    An agent sends no logs unless it runs with `MERIDIAN_LOGS=1`, and then only for Kamal's containers, checked on the server.

    The page you open hands its channel a signed grant, bound to you, for exactly the containers it shows, and the channel streams nothing else. Lines pass through the Solid Cable database, which keeps messages for one minute, and are written nowhere else.
  </Accordion>
  <Accordion title="Access ends at once">
    - Revoking an agent token closes its open connections. Meridian also checks each agent connection's token again every 60 seconds.
    - Signing out closes your open streams.
    - A new password signs you out of every other session, and closes the streams those sessions had open.
  </Accordion>
  <Accordion title="Everything has a limit">
    | Action | Limit |
    | --- | --- |
    | Sign in | 10 tries in 3 minutes |
    | Snapshots | 120 a minute per token, or per token and server for a fleet token, with 12,000 a minute for the whole fleet token |
    | Deploy, Roll back | 10 a minute each |
    | Redeploy | 5 a minute |
    | Add or set a secret | 20 a minute |

    Meridian refuses a snapshot over 1 MiB before it parses it.
  </Accordion>
  <Accordion title="First run, browser rules and the audit trail">
    - **First run.** Creating the account needs the setup code from Meridian's log. So whoever reaches a fresh install first can't take it over.
    - **Content Security Policy.** Scripts and styles load only from Meridian's own origin, or inline with a nonce. No framing, no plugins, and forms post only to Meridian and GitHub.
    - **Host check.** In production, Meridian answers only to `MERIDIAN_URL`'s host. That blocks DNS rebinding and forged `Host` headers.
    - **One user.** Meridian has one account, made at first run. It can do everything Meridian can, so give it a long, unique password.
    - **Audit trail.** Every change Meridian makes is an event. Every commit it makes for you carries a `Meridian-Actor:` trailer.
  </Accordion>
</AccordionGroup>

## Known limits

- Meridian trusts snapshots as reported. A server someone has taken over can lie about what it runs. It can't change Git.
- A personal access token in `GITHUB_TOKEN` acts as its owner everywhere. Use it for a homelab, not production.

## Report a vulnerability

Report it privately through [GitHub's reporting form](https://github.com/bigint/meridian/security/advisories/new). Don't open a public issue. See `SECURITY.md` in the repository.
