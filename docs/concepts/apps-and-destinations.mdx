An [app](/reference/glossary#app) in Meridian is one Kamal config plus one destination. This page shows how Meridian finds your configs in Git and turns them into apps.

## The idea

A [config](/reference/glossary#config) is a Kamal file, such as `config/deploy.yml`, that says what an app is and which servers run it. A [destination](/reference/glossary#destination) is a variant of it, such as `production`, kept in a file like `config/deploy.production.yml`.

An app is what one `kamal deploy -c <config> -d <destination>` deploys. So each app has one version and one row on the board. Its name is its service, then its destination: `shop · production`. A config with no destinations is one app, named by its service.

## An example

This [infra repository](/reference/glossary#infra-repository) has two configs, for the services `shop` and `blog`:

<Tree>
  <Tree.Folder name="config" defaultOpen>
    <Tree.File name="deploy.yml" />
    <Tree.File name="deploy.staging.yml" />
    <Tree.File name="deploy.production.yml" />
    <Tree.File name="deploy.staging.version" />
    <Tree.File name="deploy.production.version" />
    <Tree.File name="deploy-blog.yml" />
    <Tree.File name="deploy-blog.version" />
  </Tree.Folder>
</Tree>

Meridian finds three apps:

| App | Config | Destination | Version file |
| --- | --- | --- | --- |
| `shop · production` | `config/deploy.yml` | `production` | `config/deploy.production.version` |
| `shop · staging` | `config/deploy.yml` | `staging` | `config/deploy.staging.version` |
| `blog` | `config/deploy-blog.yml` | none | `config/deploy-blog.version` |

There is no plain `shop` app. A config with destination files is never an app by itself.

<Warning>
`config/deploy.blog.yml` would be the `blog` destination of `config/deploy.yml`, not an app of its own, because `kamal deploy -c config/deploy.yml -d blog` loads it. Name separate apps with a `-`, as **New app** does.
</Warning>

## How Meridian finds configs

Each [project](/guides/projects) has **Config paths**, a comma-separated list of file patterns. The default is `config/deploy*.yml`. Only `.yml` and `.yaml` files count.

A matched file named `<base>.<name>.yml` is a destination file when `<base>.yml` or `<base>.yaml` also matches. Every other matched file is a base config.

With `kamal/*.yml`, the files `kamal/shop.yml` and `kamal/shop.staging.yml` become the app `shop · staging`.

<Accordion title="Edge cases">
  In a pattern, `*` stops at `/`, and `**/` crosses folders.

  Meridian reads an app's release history again only when its config, destination file or version file changed.

  To place a parse error, Meridian takes the key path that Kamal reports, such as `servers/web/hosts`, and finds that key's line in the YAML.

  **New app** writes a config to the project's first config path with exactly one `*` in it. It puts the service name in place of the `*`. With `config/deploy*.yml`, the service `shop` gets `config/deploy-shop.yml`. With `kamal/*.yml`, it gets `kamal/shop.yml`. A path with `**/` counts as the same path without it. See [Add a new app](/guides/new-app).
</Accordion>

## What Meridian reads from a config

Meridian parses each config and destination with Kamal itself, and keeps these values:

| Value | From |
| --- | --- |
| Service | `service` |
| Image | `image` |
| Roles and their hosts | `servers`. Each host becomes a [server](/concepts/servers-and-agents), and each role on it an assignment. |
| Accessories | `accessories`, with their hosts and images |
| Hostnames | `proxy.host` and `proxy.hosts` of every role that runs kamal-proxy |
| Secret names | `env.secret`, per-role and per-tag `env.secret`, accessories' `env.secret`, and `registry.password` when it is a list |
| Kind | The `meridian.kind` label |
| Source repository | The `meridian.source` label |

Meridian never asks Kamal for a secret's value. Only the names reach the [Secrets](/guides/secrets) page.

## Kind and source repository

Two labels in the config say what an app is and where its code lives:

```yaml config/deploy.yml
service: shop
image: acme/shop

labels:
  meridian.kind: rails
  meridian.source: acme/shop
```

- `meridian.kind` is `static`, `node`, `rails`, `other` or `accessories`. With no label, or any other value, the kind is `other`. **New app** writes the label for you.
- `meridian.source` is the GitHub repository with the app's code and Dockerfile, as `owner/name`. The app's page shows it as **Source**.

If you remove a label from the config, the next sync clears it in Meridian too.

## Configs that only run accessories

A config labelled `meridian.kind: accessories` runs only accessories, such as the `cloudflared` connectors of a [Cloudflare Tunnel](/guides/cloudflare-tunnel). Meridian leaves it off the board and the map. It refuses to deploy, redeploy or roll it back. Start its accessories with `kamal accessory boot all -c <config>`.

## When a config changes or breaks

If a config fails to parse, its app keeps the last good parse, with its deploys and releases. The project's page shows the error with its file and line.

If you delete a config, its app goes at the next sync, with its deploys and releases.
