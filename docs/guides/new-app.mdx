The **New app** form turns a few answers into a [Kamal](/reference/glossary#kamal) [config](/reference/glossary#config), the file that says what an app is and where it runs. Meridian checks it and opens a pull request on your [infra repository](/reference/glossary#infra-repository). Nothing runs until you merge. Then CI deploys the first version.

You need the admin role. The form is at **Apps** → **New app**, or **New app** on the board. See [Roles](/concepts/roles).

## Fill in the form

<Steps>
  <Step title="The app">
    - **Infra repository**: the project the config goes into.
    - **Name**: Kamal's `service`. Lowercase letters, digits, `-` and `_`, starting with a letter or digit, at most 63 characters.
    - **Source repository**: where the app's code and Dockerfile live, as `owner/name`. The image is named after it, in lowercase.
    - **Kind**: what the app is. It sets the default port and the Dockerfile guidance. See [Kinds](#kinds).
    - **Hostname**: the domain the app answers on, such as `shop.example.com`.
  </Step>
  <Step title="Where it runs">
    - **Servers**: pick one or more, grouped by their `region` label. Hold ⌘ or Ctrl to pick several.
    - **…or every server with these labels**: a label selector such as `role=web,region=sgp`. It replaces the servers picked above. The config lists every server whose labels match all the terms.
    - **Destination**: optional, such as `production`. Meridian then writes a base config plus a [destination](/reference/glossary#destination) file, a variant of the config.
    - **Port**: the port the app listens on inside its container. Leave it blank for the kind's default.
    - **Registry**: the registry host, `ghcr.io` by default. A port and a path are allowed, such as `registry.example.com:5000/team`.
    - **First version**: the image tag CI deploys when you merge, `latest` by default. It follows the [version format](/guides/deploy#version-format).
  </Step>
  <Step title="Open the pull request">
    Click **Open pull request**. If a check fails, the form comes back with every reason at the top, and each one next to its field. See [If a check fails](#if-a-check-fails). If all pass, you land on the proposal page.
  </Step>
</Steps>

### Kinds

| Kind | For | Default port |
| --- | --- | --- |
| Static | a static site served by nginx | `80` |
| Node | a Next.js app (standalone output) | `3000` |
| Rails | a Rails app, behind Thruster | `80` |
| Other | any container | `3000` |

A Rails app also gets `RAILS_MASTER_KEY` under `env.secret`. Meridian stores the kind in the config as the label `meridian.kind`. A config without the label counts as **Other**.

## The proposal

Meridian opens a pull request on the infra repository. Its branch is `meridian/new-shop-<6 hex digits>`, and its title is `feat(shop): add node app`. The body lists the config, hosts, URL and first version, a **Before merging** checklist, and the Dockerfile guidance.

The proposal page says `shop is ready for review`, with **Open pull request #12**. Its sections are:

- **Still to do by hand**: the same checklist as the pull request.
- **Files**: every file Meridian wrote, in full.
- **Dockerfile for acme/shop**: the guidance for the kind.

If the project lets admins commit directly, Meridian commits the files to the default branch instead. The page then says `shop is committed`, with **View commit**. See [Projects](/guides/projects#direct-commits).

<Warning>
A direct commit deploys the first version straight away. On such a project, do the steps in [Before you merge](#before-you-merge) before you click **Open pull request**.
</Warning>

## Before you merge

Merging is the deploy. It puts the [version file](/reference/glossary#version-file) on the branch, so CI runs `kamal deploy` with the first version. Do these steps first. The pull request's checklist names them with your values.

<Steps>
  <Step title="Point DNS at the servers">
    Point the hostname at the servers, or at the tunnel or load balancer in front of them. If the servers are behind NAT, route the hostname through your tunnel to port 80 or 443 on them.
  </Step>
  <Step title="Add a Dockerfile and push an image">
    Add a Dockerfile to the source repository, following the [guidance](#dockerfile-guidance) below. Have its CI push `ghcr.io/acme/shop:<tag>`. The deploy workflow never builds, so the first version must already be in the registry.
  </Step>
  <Step title="Check the secrets">
    The infra repository needs the `KAMAL_REGISTRY_PASSWORD` secret, plus `RAILS_MASTER_KEY` for a Rails app. Set them on the [Secrets](/guides/secrets) page. `.kamal/secrets` must read them, such as `KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD`.
  </Step>
  <Step title="Serve it through the tunnel, if you have one">
    The checklist names the tunnel's connector servers. Run the app on all of them, and add a route for its hostname to `http://kamal-proxy:80`.
  </Step>
  <Step title="Merge">
    Merge the pull request. From then on, you deploy with the app's **Deploy** button.
  </Step>
</Steps>

## After the merge

Within 30 seconds Meridian reads the new config. The app appears on the board, and **Current deploy** on its page follows the first deploy. The files are yours from then on. Edit them like any Kamal config.

## If a check fails

Meridian never proposes a config that would clash with another app, or that Kamal would reject.

| Check | Message |
| --- | --- |
| Required fields | **Infra repository**, **Name**, **Source repository** and **Hostname** can't be blank. The list at the top calls them `Project`, `Service`, `Source repo` and `Hostname`. |
| Name, source repository, hostname, destination, port and registry formats | Such as `must look like owner/name`, `must be a domain name` or `must be a registry host, such as ghcr.io`. The port must be from 1 to 65535. |
| Label selector syntax | `must be labels like role=web, separated by commas`. Every term is `key=value`. |
| At least one server | `Choose at least one server, or a label selector that matches some`. |
| Servers that can be written into a config | `Can't write these servers into a config, their hostnames aren't host names: ...`. A hostname must start with a letter or digit and hold only letters, digits, `.`, `_`, `:` and `-`, so no spaces, quotes or `<%`. |
| The config path is one the project reads | `... isn't matched by the project's config paths (...), so Meridian would never see it. Add a path with a * to the project.` |
| No other config at that path | `already has a config at config/deploy-shop.yml`. Any destination of an existing config counts too. |
| No other app with that service and destination | `is already the service of shop, in config/deploy-shop.yml`. Two such configs in one project would name the same containers. |
| No other app on that hostname | `is already served by shop`. kamal-proxy gives a hostname to one service. Every project counts. |
| No file in the way | `config/deploy-shop.yml already exists in acme/infra`. Meridian never replaces a file, even one it doesn't list as an app, such as a config Kamal can't parse. |
| Kamal accepts it | `Kamal rejected the generated config: ...`. Meridian parses the result with the same Kamal version that reads your configs. |

## Where the config goes

Meridian names the file from the project's config paths, the patterns that say where its configs live. It takes the first pattern with exactly one `*` and puts the service name in place of the `*`.

| Project config path | Config for `shop` |
| --- | --- |
| `config/deploy*.yml` (the default) | `config/deploy-shop.yml` |
| `deploy/*.yml` | `deploy/shop.yml` |
| `deploy/**/*.yml` | `deploy/shop.yml` |
| `kamal/*/deploy.yml` | `kamal/shop/deploy.yml` |

If no path fits, add one with a `*` on the project's **Edit** page. See [Projects](/guides/projects#choose-config-paths).

<Accordion title="Edge cases">
  A `**/` doesn't count as a `*`. When the text before the `*` doesn't end in `/`, `.`, `-` or `_`, Meridian adds a `-`. If no path has a single `*`, Meridian falls back to `config/deploy*.yml`. That result must still match one of the project's config paths, or the check fails.
</Accordion>

## The files it writes

For a Node app named `shop` from `acme/shop` on two servers, without a destination:

<CodeGroup>
```yaml config/deploy-shop.yml
# shop: a Next.js app (standalone output)
# Generated by Meridian. This file is yours: edit it like any Kamal config.
service: shop
image: acme/shop

# Meridian reads these labels to know the app's kind and source repository.
labels:
  meridian.kind: node
  meridian.source: acme/shop

servers:
  web:
    - web-1.example.com
    - web-2.example.com

proxy:
  host: shop.example.com
  app_port: 3000
  healthcheck:
    path: /up

registry:
  server: ghcr.io
  username: acme
  password:
    - KAMAL_REGISTRY_PASSWORD

builder:
  arch: amd64
```

```text config/deploy-shop.version
latest
```
</CodeGroup>

With a destination, `servers` and `proxy.host` move from the base config into the destination file. The version file carries the destination's name. For a Rails app with the destination `production`:

<CodeGroup>
```yaml config/deploy-shop.yml
# shop: a Rails app
# Generated by Meridian. This file is yours: edit it like any Kamal config.
service: shop
image: acme/shop

# Meridian reads these labels to know the app's kind and source repository.
labels:
  meridian.kind: rails
  meridian.source: acme/shop

proxy:
  app_port: 80
  healthcheck:
    path: /up

env:
  secret:
    - RAILS_MASTER_KEY

registry:
  server: ghcr.io
  username: acme
  password:
    - KAMAL_REGISTRY_PASSWORD

builder:
  arch: amd64
```

```yaml config/deploy-shop.production.yml
# shop in production. Generated by Meridian.
servers:
  web:
    - web-1.example.com

proxy:
  host: shop.example.com
```

```text config/deploy-shop.production.version
latest
```
</CodeGroup>

The `meridian.source` label records the source repository, and the app's page shows it. If the project has a [Cloudflare Tunnel](/guides/cloudflare-tunnel), the config also logs Cloudflare's visitor headers under `proxy.logging`, for the [Traffic](/guides/traffic) page.

## Dockerfile guidance

Every image must listen on the configured port and answer `GET /up` with a `200` once it is ready. Kamal starts only images labelled with their service. `kamal build` adds the label. If your CI builds the image another way, keep the `LABEL service="shop"` line.

<Tabs>
  <Tab title="Static">
    Build the site into `dist/`, adjusting the path, then serve it with nginx.

    ```dockerfile Dockerfile
    FROM nginx:1.27-alpine
    LABEL service="shop"
    COPY nginx.conf /etc/nginx/conf.d/default.conf
    COPY dist/ /usr/share/nginx/html/
    ```

    ```nginx nginx.conf
    server {
      listen 80;
      root /usr/share/nginx/html;
      location = /up { access_log off; return 200 "OK"; }
      location / { try_files $uri $uri/ $uri.html =404; }
    }
    ```
  </Tab>
  <Tab title="Node">
    A server-rendered Next.js app in `standalone` output mode.

    ```js next.config.js
    module.exports = { output: "standalone" }
    ```

    Add a health check at `/up`:

    ```js app/up/route.js
    export function GET() { return new Response("OK") }
    ```

    ```dockerfile Dockerfile
    FROM node:22-alpine AS build
    WORKDIR /app
    COPY package*.json ./
    RUN npm ci
    COPY . .
    RUN npm run build

    FROM node:22-alpine
    LABEL service="shop"
    WORKDIR /app
    ENV NODE_ENV=production PORT=3000 HOSTNAME=0.0.0.0
    COPY --from=build /app/.next/standalone ./
    COPY --from=build /app/.next/static ./.next/static
    COPY --from=build /app/public ./public
    EXPOSE 3000
    CMD ["node", "server.js"]
    ```
  </Tab>
  <Tab title="Rails">
    Rails 8 ships a production `Dockerfile`, with Thruster on port 80, and a `/up` health check. Use them as `rails new` generates them. If your CI builds the image without `kamal build`, add `LABEL service="shop"`.
  </Tab>
  <Tab title="Other">
    Any image works. It must listen on the configured port, answer `GET /up` with a `200` once it is ready, and carry `LABEL service="shop"`.
  </Tab>
</Tabs>

To change what every new app gets, edit `templates/dockerfiles/<kind>.md` for the guidance and `templates/kamal/app.yml` for the config.
