This page walks through Meridian one screen at a time, in the order of the sidebar. The sidebar holds the screens you watch at the top, and under **Manage** the screens that set Meridian up. Admins also see **Settings** and **Jobs** at the bottom.

Every screen updates itself. When an agent reports a change or a deploy moves on, open pages redraw in place, without losing your scroll position.

Viewers see every screen. Buttons that a person's role doesn't allow are hidden. See [roles](/concepts/roles).

## Board

The board, at `/`, answers one question: does every server run what Git says? The header counts the apps and servers, and says **all matching Git** when every cell is in sync.

<Screenshot name="board" alt="The board: Getting started, Needs attention, and the grid of every app on every server, with the inspector open on the right" />

Admins see **New app** at the top right. On a new install, **Getting started** lists three steps and ticks each one off as it happens: connect your infra repository, put the agent on your servers, deploy something. It goes away when all three are done.

### Needs attention

**Needs attention** lists what a person should look at, worst first, as plain sentences:

| State | Sentence | Button |
| --- | --- | --- |
| Missing | **shop** isn't running on **web-1**, but Git says it should. | **Open shop** |
| Drifted | **shop** on **web-1** runs `v41`, not `v42` from Git. | **Open shop** |
| Stray | **shop** is running on **web-9**, but Git doesn't put it there. | **Open shop** |
| Stale | **web-1**'s agent has gone quiet. | **Open server** |

A second line says what the state probably means, such as **A deploy may still be rolling out, or it stopped part-way.** A quiet server is one item, however many apps run on it. When more than three servers are quiet, they become one item, **5 agents have gone quiet**, with **See agents**. The board shows four items, and the rest under **more things need attention**. The number next to **Board** in the sidebar counts the whole list.

### Every app on every server

The grid shows each app against each server it runs on or should run on. Each cell shows the version the server runs, marked by its [drift state](/concepts/drift). Hover over a cell to see the app, the server, the state and the running version. The **Git** column shows each app's newest release.

Above the grid:

- **The state chips** count the cells in each state. Press one, such as **Drifted**, to show only those cells. Press it again, or **All**, to show every cell.
- **Apps × servers** and **Servers × apps** turn the grid around, so servers become the rows.
- **Filters** narrow the grid by **App**, **Project**, **Region**, **Provider** and **Role**, and pick **Group by**. **Automatic** groups by region above 30 servers, or when servers use more than one region. **Nothing** turns grouping off.
- **What do these mean?** explains each state.

The grid shows 25 rows a page. Every filter, the page and the open app live in the URL, such as `/?state=drifted&region=sgp`, so you can share a view as a link.

### The inspector

Click an app's name in the grid, and the inspector opens on the right, at `/?inspect=<app id>`. It shows:

- the app's kind and project, and how many servers run its newest release, such as **2 of 3 servers run v12**,
- **Ship a version**, for deployers: type a version and press **Deploy**,
- **Servers**, each with the version it runs and its place,
- **Recent releases**, the last three,
- **Redeploy** and **Roll back** for deployers, and **Open app page**.

See [deploy and roll back](/guides/deploy).

## Search

The search box at the top of every page finds apps, servers and projects as you type. It matches an app's service or destination, a server's name or hostname, and a project's name or repository.

<Screenshot name="search" alt="Search results for a partial name: apps, servers and projects, best match first" />

It shows the eight best matches. A name that starts with what you typed comes first, then shorter names. Press <kbd>Enter</kbd> to open the first match, or <kbd>Esc</kbd> to clear the box.

## Map

The map, at `/map`, puts every located server on a world map. Servers within 60 km of each other share one dot, a place, coloured by the worst state among its cells. A line joins two places that run the same app, thicker when they share more apps.

<Screenshot name="map" alt="The world map: places as coloured dots, lines between places that share apps, and the selected place's servers on the right" />

When an admin sets **Where Meridian runs** in [Settings](/operate/settings), the map also draws Meridian itself, with agent reports flowing in and deploys flowing out.

- **The chips** above the map count the places in each state that needs attention, and the places with a deploy under way. With two to eight apps, a row of app chips filters the map to one app.
- **Filters** narrow the map by **App**, **Project**, **Region**, **Provider** and **Role**.
- **Click a place** to see its servers, what each one runs, and the other places that share its apps.
- **Places** lists every place, worst first, with its region, its cells and whether its agents report.

A server needs a location to appear. Its agent can send `lat` and `lng` labels, or an admin can set one on the server's page. The map lists the servers that have none. See [board and map](/guides/board-and-map).

## Apps

**Apps**, at `/apps`, lists every Kamal config in your infra repositories, one row per destination. Each row shows the app, its project, its kind, its hostnames, its config file and its latest release. **Search apps** filters the list.

### New app

Admins press **New app** on the board to add an app. Meridian writes a Kamal config from a template, checks it with Kamal, and opens a pull request on the infra repository. The form asks for:

| Field | What it sets |
| --- | --- |
| **Infra repository** | The project the config goes to. |
| **Name** | The Kamal service. |
| **Source repository** | Where the app's code and Dockerfile live, as `owner/name`. Previews watch its pull requests. |
| **Kind** | **Static** (nginx, port 80), **Node** (Next.js, port 3000), **Rails** (port 80) or **Other** (port 3000). |
| **Hostname** | The domain that kamal-proxy serves the app on. |
| **Servers** | The servers to run on, or **every server with these labels**, such as `role=web,region=sgp`. |
| **Destination** | Optional. Writes a base config plus a destination file. |
| **Port**, **Registry**, **First version** | The app port, the registry host, and the image tag to deploy once the pull request is merged. |

Press **Open pull request**. The next page lists the files, what is **Still to do by hand**, and Dockerfile guidance for the kind. The app appears on the board once the pull request is merged. See [add a new app](/guides/new-app).

## App page

The app's page, at `/apps/<id>`, has everything about one app. The header shows its kind, its project, its hostnames as links, and how many servers run its newest release.

<Screenshot name="app" alt="An app's page: servers with their versions and health, releases with Roll back, and Ship a version on the right" />

- **Traffic** and **Logs**, for deployers, open the app's live request lines and container logs. See [traffic](/guides/traffic) and [live stats and logs](/guides/live-stats-and-logs).
- **Servers** lists each server with the version it runs, its state, its roles, its health and its place.
- **Accessories** lists the config's accessories, such as a database, with their image, server, state and start time.
- **Releases** lists the last 20 releases from the Git history of the version file. The newest has **Roll back**.
- **Configuration** shows the config file, the image, the roles, the version file, the source repository and the secret names.

On the right, **Ship a version** takes a version and commits it with **Deploy**. Its box suggests past releases. **Redeploy** runs the deploy workflow again for the current version. **Current deploy** shows the last deploy: its CI status, who started it, its commit, a link to the CI run, and each server's progress as its agent reports the new version.

## Servers

**Servers**, at `/servers`, lists every machine that Git names or an agent reports from. Each row shows the server, its hostname, its place, its labels, its agent version and when it was last seen. A quiet server is marked **silent**. **Search servers** filters by name or hostname, and **Only silent agents** shows only quiet servers.

## Server page

A server's page, at `/servers/<id>`, shows one machine. The header says **Reporting**, **No agent yet**, or **stale** with **agent silent**.

<Screenshot name="server" alt="A server's page: live host tiles, the apps on it, and every container with live CPU, memory and network" />

- **Host** shows live CPU, memory, load and disk, with a sparkline each, while the page is open. These need the agent's `/proc` mount.
- **Apps** lists each app here with the version it runs, its state and its roles.
- **Containers** lists every container that Kamal started, with its version, state, health, live CPU, memory and network, and start time. Deployers get a **Logs** button on each row.
- **Machine** shows the hostname, the agent version, when it was last seen, its location and its projects.
- **Labels** shows what the agent sent in `MERIDIAN_LABELS`.
- **Location on the map**, for admins, sets a **Latitude** and **Longitude** with **Save location**.

See [servers and agents](/concepts/servers-and-agents).

## Activity

**Activity**, at `/events`, is the audit log: everything Meridian did, and who asked for it. Entries are grouped by day, newest first, 50 to a page.

<Screenshot name="activity" alt="The activity log: deploys, rollbacks and syncs grouped by day, each with who did it and its commit" />

Each entry shows a sentence, such as **Deployed shop · production to v42**, the person, the action name such as `app.deploy`, the commit and a link to the pull request where there is one. Under **Filters**, **Action starts with** takes a prefix such as `app.` or `preview.`, and **Who** picks a person. See [activity events](/reference/activity-events) for every action name.

## Previews

**Previews**, at `/previews`, lists the running preview of each open pull request. Each row shows the app, the pull request with its head commit, the preview's URL, its state and when it expires. States are **Deploying**, **Active**, **Failed** and **Removing**. Deployers can press **Destroy** to remove one now.

**Recently removed** lists the last ten previews that went away, and when. See [previews](/guides/previews).

## Projects

**Projects**, at `/projects`, lists your infra repositories, each with its app count, its last sync and its problems. Admins add one with **Add project**.

A project's page has:

- **Sync now**, to read Git at once instead of within 30 seconds,
- **Add CI workflow**, to open a pull request with `.github/workflows/meridian-deploy.yml`,
- **Edit**, for the repository, branch, installation ID and config paths, and **Remove project** at the bottom of that form,
- **Repository**, with the branch, the config paths, the last sync and whether changes arrive as pull requests or direct commits,
- **Parse errors**, each with its file and line,
- **Configs found**, every app with its config, destination, server count and hostnames.

Removing a project removes it from Meridian only. Nothing in Git changes. See [projects](/guides/projects).

## Agents

**Agents**, at `/agents`, is where servers get connected. **Install** shows the two Kamal accessories to add, with your Meridian URL filled in. **Connect a server** lists the steps.

Admins create a token with **Create token**. Give it a **Label**, and tick **Fleet token, shared by many servers** for a token that many servers share. Meridian shows the token once. **Tokens** lists every token with its server and when it was last used. **Revoke** cuts it off.

**Silent agents** lists every server whose agent has gone quiet, then the servers that no agent has ever reported from. See [install the agent](/guides/agent).

## Tunnels

**Tunnels**, at `/tunnels`, shows each Cloudflare Tunnel that your configs run. Each tunnel shows its token secret and whether Meridian set it, how many connectors run, the apps it serves, and anything that needs fixing.

**Set up a tunnel** walks through the steps in order: in Cloudflare, in Git, on the servers, and back in Cloudflare for the routes. Admins can press **Edit connectors** to choose the servers that run a connector, which Meridian proposes as a change to the config. Meridian never calls Cloudflare's API. See [Cloudflare Tunnel](/guides/cloudflare-tunnel).

## Secrets

**Secrets**, at `/secrets`, lists the secret names each project's configs use, from `env.secret` and `registry.password`. Each row shows the apps that use the name and when it was last set from Meridian.

Admins type a value under **Set or rotate**. Meridian encrypts it for the repository's GitHub Actions secrets and keeps nothing. **Add another name** adds a name that no config uses yet, with an optional value. See [secrets](/guides/secrets).

## Settings

**Settings**, at `/settings`, is for admins. It has two tabs.

**General** has three cards, saved together with **Save**:

- **Workspace**: the **Name** of this Meridian.
- **Previews**: the preview **Domain**, **Hostnames** in nested or flat form, the **Preview servers** label selector, and **Expire after (days)**.
- **Where Meridian runs**: a **Place**, **Latitude** and **Longitude**, the centre of the map's flows.

Beside them, **Connections** shows how Meridian reaches GitHub, whether webhooks are on, and the Kamal version it parses configs with. These come from the environment and can't be changed here.

**People** lists everyone with their role. **Add person** adds someone with a password. **Edit** changes their details or role. See [settings](/operate/settings) and [people](/guides/people).

**Jobs**, in the sidebar, opens the background jobs dashboard at `/jobs`.

## The account menu

Your name at the top right opens the account menu. It shows your role, a **Theme** switch between **System**, **Light** and **Dark**, and **Sign out**. The theme is saved in the browser, not on your account. The sidebar's **Collapse sidebar** button shrinks it to a rail of icons.
