The [agent](/reference/glossary#agent) is a small program on each server that tells Meridian what is running there. Without it, the board knows only what Git says, and every cell shows **Unknown**.

The agent only reads, and it only connects out to Meridian, so it works behind NAT and firewalls. Every 15 seconds it sends a snapshot of the server's [Kamal](/reference/glossary#kamal) containers. For each one, that is its name, image, labels, version, state and health.

It never sends environment variables, commands, entrypoints or mounts, which can hold secrets. Live stats and logs flow only while someone is looking, and logs only if you turn them on. The full list is in [Agent protocol](/reference/agent-protocol).

## Before you start

- A Kamal [config](/reference/glossary#config) whose `servers` include every server you want to watch. The agent runs as two accessories of that config. An accessory is an extra container Kamal runs beside your app.
- A `MERIDIAN_URL` that each server can reach, such as `https://meridian.example.com`. Every proxy in front of Meridian must pass WebSockets through to `/cable`. [kamal-proxy](/reference/glossary#kamal-proxy) and Thruster both do.

## Install with Kamal

<Steps>
  <Step title="Create a token">
    Open **Agents** under **Manage**. Under **Connect a server**, type a **Label**, such as `web-1`.

    If one token will serve several servers, tick **Fleet token, shared by many servers**. See [One token per server, or one for the fleet](#one-token-per-server-or-one-for-the-fleet). Click **Create token**.

    Copy the token from **Copy this token now**. Meridian can't show it again.
  </Step>
  <Step title="Give Kamal the token">
    Add this line to the secrets file Kamal reads for the config, such as `.kamal/secrets`:

    ```bash .kamal/secrets
    MERIDIAN_TOKEN=$MERIDIAN_TOKEN
    ```

    Then export `MERIDIAN_TOKEN` in the shell you run Kamal from. You can also read it from your password manager in that line.
  </Step>
  <Step title="Add the two accessories">
    Copy them from **Install** on the **Agents** page, which fills in your `MERIDIAN_URL`. The same text is in `templates/kamal/agent-accessories.yml`.

    Put them under `accessories:`. Replace `SERVICE` with the config's `service`, and `REGION` and `PROVIDER` with your own labels.

    `roles: [ web ]` starts them on the config's `web` servers only. To cover more, list every role whose servers should report, or name the servers with `hosts:`.

    ```yaml config/deploy.yml
    accessories:
      meridian_docker:
        # Read-only Docker API: only GETs under /containers (list, inspect
        # and, while someone is looking, stats and logs).
        image: tecnativa/docker-socket-proxy:v0.4.1
        roles: [ web ]
        network: meridian
        env:
          clear:
            CONTAINERS: 1
            POST: 0
        volumes:
          - /var/run/docker.sock:/var/run/docker.sock:ro

      meridian_agent:
        image: ghcr.io/bigint/meridian-agent:v0.1.7
        roles: [ web ]
        network: meridian
        env:
          clear:
            MERIDIAN_URL: https://meridian.example.com
            DOCKER_HOST: tcp://shop-meridian_docker:2375
            MERIDIAN_LABELS: region=sgp,provider=ovh
            MERIDIAN_LOGS: 1
          secret:
            - MERIDIAN_TOKEN
        volumes:
          - /etc/machine-id:/host/etc/machine-id:ro
          - /etc/hostname:/host/etc/hostname:ro
          - /proc:/host/proc:ro
    ```
  </Step>
  <Step title="Create the network">
    Once per server, create the `meridian` Docker network that the two accessories share. Kamal creates only its own `kamal` network.

    ```bash
    kamal server exec "docker network inspect meridian >/dev/null 2>&1 || docker network create meridian"
    ```
  </Step>
  <Step title="Boot them">
    ```bash
    kamal accessory boot meridian_docker
    kamal accessory boot meridian_agent
    ```

    `kamal deploy` never starts accessories, so you always run this step by hand.
  </Step>
  <Step title="Check it reports">
    On **Agents**, the token's **Last used** shows a time, and a per-server token shows its server. The server's page says **Reporting**. The board fills in its cells within one interval, 15 seconds by default.
  </Step>
</Steps>

<Warning>
Keep both accessories on their own `meridian` network. Never put them on Kamal's `kamal` network, where your apps run. The socket proxy gives anyone who reaches port 2375 every container's environment, files and logs. Never publish that port on the server.
</Warning>

On the `meridian` network, the agent reaches `MERIDIAN_URL` like the server itself does, by hostname or IP address. It can't reach a container on the `kamal` network by name.

<Accordion title="How this works under the hood">
  **`meridian_docker`** is [`tecnativa/docker-socket-proxy`](https://github.com/Tecnativa/docker-socket-proxy). With `CONTAINERS=1` and `POST=0`, it allows only `GET` requests under `/containers`. The agent talks to Docker only through it, so even an agent someone has taken over can't start, stop or exec into containers. A socket mounted `:ro` alone is not read-only.

  **`meridian_agent`** is a static Go binary of about 7 MB, on a distroless image, running as `nonroot`. It reads the machine ID and hostname from the two mounted files, and the server's CPU, memory and load from `/proc`. Without the `/proc` mount, the server page shows per-container numbers only.

  The agent finds Kamal containers by Kamal's `service`, `role` and `destination` labels and by the name `kamal-proxy`. It takes each version from the container name, as Kamal does.
</Accordion>

## One token per server, or one for the fleet

| | Per-server token | Fleet token |
| --- | --- | --- |
| Binds to | The first machine that uses it | Nothing. Each server is known by its machine ID. |
| Another machine uses it | Refused with `422`: `This token belongs to another server. Give each server its own token, or use a fleet token`. The agent logs the refusal. | Accepted, as its own server |
| A server with a token of its own | | Refused with `422`: `This server has a token of its own. Use that token, or revoke it to report with a fleet token` |
| Revoking it silences | One server | Every server that uses it |
| **Server** column on **Agents** | The server, or `binds on first contact` | `many` |

Every machine with a fleet token can report as any other server that uses it, so a fleet token is only as safe as the least safe of those machines. Kamal gives every server of an accessory the same secret. So if the accessories run on several servers, use a fleet token, or give each server its own accessory and token.

To revoke a token, click **Revoke** in its row on **Agents** and confirm. Meridian refuses its snapshots from then on and closes its WebSocket at once.

## Matching servers to Git

Git names a server by the host Kamal connects to, such as `web-1.example.com`. The agent reports the machine's own hostname. Meridian matches the two in this order:

1. The exact hostname.
2. The first DNS label, when only one server has it. `web-1` matches `web-1.example.com`.
3. An IP address, matched only whole.

When nothing matches, set `MERIDIAN_HOSTNAME` on the agent to the name in your config. Then reboot the agent.

```yaml
env:
  clear:
    MERIDIAN_HOSTNAME: web-1.example.com
```

Servers whose agent never reported are listed under **Silent agents** on the **Agents** page.

A server can also report before Git lists it, or be rebuilt with a new machine ID. [Servers and agents](/concepts/servers-and-agents) explains how Meridian matches those.

## Labels and map location

`MERIDIAN_LABELS` sets the labels the board filters and groups by, as comma-separated `key=value` pairs. Any key works. Four have a use in Meridian:

| Label | Used for |
| --- | --- |
| `region` | Board filter and grouping, map place names, and the server's place |
| `provider` | Board filter and grouping |
| `role` | Board filter and grouping, and label selectors for new apps |
| `city` | Map place names, and the server's place |

To put the server on the map, add `lat` and `lng` in decimal degrees.

```yaml
MERIDIAN_LABELS: region=sgp,provider=ovh,role=web,city=Singapore,lat=1.35,lng=103.82
```

You can also set a location on the server's page, under **Location on the map**. An agent that reports `lat` and `lng` overrides it on its next snapshot. See [The map](/guides/board-and-map#the-map).

## Settings

The agent reads its settings from environment variables. These are the ones you are likely to change:

| Variable | Default | What it does |
| --- | --- | --- |
| `MERIDIAN_URL` | required | Meridian's base URL. |
| `MERIDIAN_TOKEN` | required | The token from **Agents**. |
| `MERIDIAN_LABELS` | none | Labels, such as `region=sgp,provider=ovh`. |
| `MERIDIAN_INTERVAL` | `15s` | Time between snapshots, at least `1s`. Each wait varies at random by up to 20%. Meridian calls a server stale after three intervals, and never sooner than 45 seconds. |
| `MERIDIAN_LOGS` | off | `1` or `true` lets you read Kamal containers' logs and traffic. |
| `MERIDIAN_LIVE` | on | `0` or `false` turns the WebSocket off: no live stats, no logs, snapshots only. |
| `MERIDIAN_HOSTNAME` | the server's `/etc/hostname` | The name the agent reports. |

Every variable, including `DOCKER_HOST` and `MERIDIAN_MACHINE_ID`, is in [Environment](/reference/environment).

To see what the agent would send without sending it, run `meridian-agent -print`. It prints one snapshot and needs no URL or token.

## Upgrade the agent

<Steps>
  <Step title="Change the image tag">
    Set `meridian_agent`'s `image` to the new tag, such as `ghcr.io/bigint/meridian-agent:v0.2.0`.
  </Step>
  <Step title="Reboot the accessory">
    ```bash
    kamal accessory reboot meridian_agent
    ```
  </Step>
  <Step title="Check the version">
    Each server's page shows the version under **Machine**, as **Agent**.
  </Step>
</Steps>

The reboot leaves a gap of a few seconds with no snapshot, well under the 45 seconds before a server turns stale.

## If something goes wrong

Read the agent's log on the server with `kamal accessory logs meridian_agent`. [Troubleshooting](/operate/troubleshooting#agents) lists each log line and status code, and the fix.
