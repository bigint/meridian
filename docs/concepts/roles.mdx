Everyone who signs in to Meridian has one of three [roles](/reference/glossary#roles). The role decides what that person can change.

## The three roles

- A **viewer** sees everything except live logs and traffic.
- A **deployer** can also deploy, roll back, and read live logs and traffic.
- An **admin** can do everything else, from adding projects to managing people.

A new person is a viewer unless an admin picks another role.

<Roles />

Every role can read every app, server, preview, tunnel, agent, secret name and activity entry. Only admins can open **Settings** and the jobs dashboard at `/jobs`. Live logs and traffic need a deployer or admin, because they can hold secrets.

Meridian hides each button that your role doesn't allow. If you send the request anyway, Meridian shows **You don't have permission to do that.** A request for something other than a page gets `403 Forbidden`.

## The first admin

A fresh Meridian has no people. Every page sends you to the welcome page, `/first_run`, which creates the first admin. It asks for a **Setup code**, a name, an email and a password.

The setup code proves that you run the server. It is 20 hexadecimal characters, worked out from `SECRET_KEY_BASE`, so Meridian stores it nowhere. Meridian writes the code to its log each time someone opens the welcome page. So open the page first, then read the code with one of these commands:

<CodeGroup>

```bash Kamal
kamal app logs | grep "setup code"
# or
kamal app exec 'bin/rails meridian:setup_code'
```

```bash Docker
docker logs meridian 2>&1 | grep "setup code"
# or
docker exec meridian bin/rails meridian:setup_code
```

</CodeGroup>

The welcome page works only while no person exists. After that, it sends everyone to sign in. The first admin lands on **Projects**, ready to add the infra repository.

<Note>
The code changes when `SECRET_KEY_BASE` changes. A new `SECRET_KEY_BASE` also signs everyone out, because Meridian signs session cookies with it.
</Note>

## Adding people and signing in

Admins add people in **Settings**, under **People**, with **Add person**. Meridian sends no email and has no single sign-on, so share each new password with its person privately. [Manage people](/guides/people) has the steps.

- A password is 12 to 72 characters long.
- Meridian always has at least one admin. The last admin can't become a deployer or viewer.
- An admin can't remove their own account.
- A new password signs that person out of every other session.
- A role change takes effect at once. Meridian closes the person's open live connections, so an open page can't keep streaming what the old role allowed.

People sign in at `/session/new` with their email and password. Meridian allows 10 tries from one IP address in 3 minutes, then shows `Try again later.`. A session lasts until the person signs out from the account menu, or an admin changes their password or removes them.

<Accordion title="How this works under the hood">
  The session cookie is signed, `HttpOnly` and `SameSite=Lax`. Behind HTTPS it is also `Secure`.

  Agents and GitHub don't sign in, and neither has a role or can open a page. Agents send a bearer token to `/agent/snapshots` and `/cable`. GitHub signs each [webhook](/reference/glossary#webhook) with the webhook secret. See [Endpoints](/reference/endpoints).
</Accordion>
