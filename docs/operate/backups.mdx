Meridian keeps its data in SQLite files under `/rails/storage`, in the `meridian_storage` Docker volume. Git already holds your configs, versions and their history. So a backup protects what only Meridian knows: your account, agent tokens and the activity trail.

## What to back up

| File | Holds | Back up |
| --- | --- | --- |
| `production.sqlite3` | Your account, sessions, projects, apps, releases, deploys, servers, agent tokens, secret names, settings and Activity | Yes |
| `production_queue.sqlite3` | Solid Queue: queued, scheduled and failed jobs | Optional. Recurring jobs are set up again on boot. |
| `production_cache.sqlite3` | Solid Cache: cached GitHub files, and which live streams are open | No. Meridian refills it. |
| `production_cable.sqlite3` | Solid Cable: messages from the last minute | No |

Without a backup, losing the volume loses your account, agent tokens and Activity. Add the projects again, and they sync from Git. Give the agents new tokens, and they report again.

## Stream changes with Litestream

[Litestream](https://litestream.io) copies each SQLite change, as it happens, to an S3-compatible bucket, such as AWS S3, Backblaze B2, Cloudflare R2 or MinIO. Run it as a Kamal accessory beside Meridian, on the same volume. An accessory is an extra container Kamal runs beside an app.

<Steps>
  <Step title="Add the accessory">
    Add this to Meridian's `config/deploy.yml`:

    ```yaml config/deploy.yml
    accessories:
      litestream:
        image: litestream/litestream:0.3.13
        host: meridian.internal.example.com
        cmd: replicate
        files:
          - config/litestream.yml:/etc/litestream.yml
        volumes:
          - "meridian_storage:/rails/storage"
        env:
          secret:
            - LITESTREAM_ACCESS_KEY_ID
            - LITESTREAM_SECRET_ACCESS_KEY
    ```

    Use the same `host` as Meridian's `web` role, so both see the same volume.
  </Step>
  <Step title="Say where to replicate">
    Create `config/litestream.yml`:

    ```yaml config/litestream.yml
    dbs:
      - path: /rails/storage/production.sqlite3
        replicas:
          - url: s3://your-bucket/meridian/production
            endpoint: https://s3.example.com   # omit for AWS
      - path: /rails/storage/production_queue.sqlite3
        replicas:
          - url: s3://your-bucket/meridian/queue
            endpoint: https://s3.example.com
    ```
  </Step>
  <Step title="Add the bucket's keys">
    Add `LITESTREAM_ACCESS_KEY_ID` and `LITESTREAM_SECRET_ACCESS_KEY` to `.kamal/secrets`. Read them from your environment or a password manager, like the other secrets.
  </Step>
  <Step title="Boot it">
    ```bash
    kamal accessory boot litestream
    kamal accessory logs litestream
    ```

    The log shows each database it replicates.
  </Step>
</Steps>

## Restore from Litestream

Litestream won't overwrite a file that exists, so move the old database aside first. Stop Meridian first, so nothing writes while you restore:

```bash
kamal app stop
kamal accessory exec --reuse litestream "sh -c 'mkdir -p /rails/storage/old && mv /rails/storage/production.sqlite3* /rails/storage/old/'"
kamal accessory exec --reuse litestream "litestream restore -o /rails/storage/production.sqlite3 s3://your-bucket/meridian/production"
kamal app boot
```

On boot, Meridian runs `bin/rails db:prepare`, which applies any migration the restored file lacks. To get back failed jobs, restore `production_queue.sqlite3` the same way.

## Take a one-off copy

The image includes the `sqlite3` command. Its `.backup` command takes a safe copy while Meridian runs:

```bash
kamal app exec --reuse "sqlite3 storage/production.sqlite3 '.backup storage/backup.sqlite3'"
```

The copy lands in the volume, at `/var/lib/docker/volumes/meridian_storage/_data/backup.sqlite3` on the host. Copy it off the host with `scp`, then delete it from the volume.

<Warning>
  Don't copy a live `.sqlite3` file with `cp`. SQLite keeps recent writes in the `-wal` file beside it, so the copy misses them. Use `.backup` or Litestream.
</Warning>
