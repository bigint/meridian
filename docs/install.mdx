This guide takes you from nothing to a board that shows every app on every server. To look around first without connecting anything, follow the [quickstart](/quickstart).

Meridian is one container with SQLite inside it. You deploy it with [Kamal](/reference/glossary#kamal), a tool that deploys apps as Docker containers to your own servers over SSH.

## Before you start

You need:

- A server for Meridian that Kamal can reach over SSH, and that can reach `api.github.com` over HTTPS.
- A DNS name for Meridian, such as `meridian.example.com`, pointing at that server. [kamal-proxy](/reference/glossary#kamal-proxy), Kamal's web proxy, gets a Let's Encrypt certificate for it. So ports 80 and 443 must be open.
- [Kamal](https://kamal-deploy.org) 2 on your machine. Meridian is tested with Kamal 2.12.0.
- A GitHub account or organisation where you can create a GitHub App, or a personal access token.
- An [infra repository](/reference/glossary#infra-repository), the Git repository that holds your Kamal configs.

<Steps>
  <Step title="Connect Meridian to GitHub">
    Meridian uses GitHub's API to read your configs, commit deploys and set secrets. Pick how it signs in to GitHub.

    <Tabs>
      <Tab title="GitHub App">
        A GitHub App reaches only the repositories you install it on. Use it for any install that other people share.

        1. Open **Settings**, **Developer settings**, **GitHub Apps**, **New GitHub App**. For an organisation, open the organisation's **Settings**, then **Developer settings**, **GitHub Apps**.
        2. Set **Homepage URL** to your Meridian URL, such as `https://meridian.example.com`.
        3. Set **Webhook URL** to `https://meridian.example.com/webhooks/github`.
        4. Set **Webhook secret** to a long random string, such as the output of `openssl rand -hex 32`. Keep it for step 3, as `GITHUB_APP_WEBHOOK_SECRET`.
        5. Give the App these repository permissions:

        <GitHubAppPermissions />

        6. Create the App and note its **App ID**.
        7. Under **Private keys**, press **Generate a private key**. GitHub downloads a `.pem` file.
        8. Press **Install App**. Pick the infra repository.
        9. Note the installation ID. After you install, it is the number at the end of the page's URL, such as `12345678` in `https://github.com/settings/installations/12345678`.

        You now have four values: the App ID, the private key, the webhook secret and the installation ID.
      </Tab>
      <Tab title="Personal access token">
        A token acts as the person who made it, on every repository they can reach. Use it for a homelab or a trial. If you set both, Meridian uses the App.

        1. In GitHub, open **Settings**, **Developer settings**, **Personal access tokens**.
        2. Create a fine-grained token for the infra repository. Give it the same repository permissions as the App:
           - **Contents**, **Pull requests**, **Actions**, **Secrets** and **Workflows**: read and write.
           - **Metadata**: read.

           A classic token with the `repo` and `workflow` scopes also works.

        3. Webhooks are optional with a token. Without them, Meridian checks GitHub every 30 seconds. To add them, open the infra repository's **Settings**, **Webhooks**, **Add webhook**, and fill in the form:

           | Field | Value |
           | --- | --- |
           | **Payload URL** | `https://meridian.example.com/webhooks/github` |
           | **Content type** | `application/json` |
           | **Secret** | A long random string. It becomes `GITHUB_APP_WEBHOOK_SECRET`. |
           | **Events** | **Pushes** and **Workflow runs** |

        You now have the token, and the webhook secret if you added webhooks. Leave the installation ID blank in step 6.
      </Tab>
    </Tabs>
  </Step>

  <Step title="Fill in config/deploy.yml">
    Clone Meridian at the release you want to run:

    ```bash
    git clone --branch v0.1.0 https://github.com/bigint/meridian
    cd meridian
    ```

    `config/deploy.yml` has five numbered placeholders to fill in. Here they are, highlighted:

    ```yaml config/deploy.yml {2,6,9,14,20}
    service: meridian
    image: ghcr.io/bigint/meridian             # 5. your registry, if you build the image yourself

    servers:
      web:
        - meridian.internal.example.com        # 1. the host to run on

    proxy:
      host: meridian.example.com               # 2. where you'll reach it
      ssl: true

    registry:
      server: ghcr.io
      username: your-github-user              # 3. a registry you can pull from
      password:
        - KAMAL_REGISTRY_PASSWORD

    env:
      clear:
        MERIDIAN_URL: https://meridian.example.com   # 4. same as proxy.host
        SOLID_QUEUE_IN_PUMA: true
      secret:
        - SECRET_KEY_BASE
        - GITHUB_APP_ID
        - GITHUB_APP_PRIVATE_KEY
        - GITHUB_APP_WEBHOOK_SECRET
    ```

    | # | Key | Set it to |
    | --- | --- | --- |
    | 1 | `servers.web` | The host Kamal connects to over SSH. |
    | 2 | `proxy.host` | The DNS name people use to reach Meridian. |
    | 3 | `registry.username` | A user that can pull from the registry. For the published image, any GitHub user with a token that can read packages. |
    | 4 | `env.clear.MERIDIAN_URL` | `https://` followed by `proxy.host`. Meridian answers only to this host. |
    | 5 | `image` | Leave it to run the published image. Set your own registry and repository only if you build the image yourself. |

    If you use a personal access token instead of an App, change the secret list:

    ```yaml config/deploy.yml
      secret:
        - SECRET_KEY_BASE
        - GITHUB_TOKEN
        - GITHUB_APP_WEBHOOK_SECRET   # only if you added webhooks
    ```

    The rest of the file keeps Meridian's SQLite databases on the `meridian_storage` volume. It also adds two commands, `kamal console` and `kamal logs`.
  </Step>

  <Step title="Provide the secrets">
    Kamal reads Meridian's secrets from `.kamal/secrets`. That file reads each one from your shell's environment. Never put a real value in the file itself.

    <Tabs>
      <Tab title="GitHub App">
        ```bash .kamal/secrets
        KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD
        SECRET_KEY_BASE=$MERIDIAN_SECRET_KEY_BASE
        GITHUB_APP_ID=$MERIDIAN_GITHUB_APP_ID
        GITHUB_APP_PRIVATE_KEY=$MERIDIAN_GITHUB_APP_PRIVATE_KEY
        GITHUB_APP_WEBHOOK_SECRET=$MERIDIAN_GITHUB_APP_WEBHOOK_SECRET
        ```

        Set the values in your shell, or read them from a password manager:

        ```bash
        export KAMAL_REGISTRY_PASSWORD=...        # a token that can pull from the registry
        export MERIDIAN_SECRET_KEY_BASE=$(openssl rand -hex 64)
        export MERIDIAN_GITHUB_APP_ID=123456
        export MERIDIAN_GITHUB_APP_PRIVATE_KEY="$(cat meridian.private-key.pem)"
        export MERIDIAN_GITHUB_APP_WEBHOOK_SECRET=...
        ```
      </Tab>
      <Tab title="Personal access token">
        Replace the three `GITHUB_APP_*` lines in `.kamal/secrets` to match the secret list in `config/deploy.yml`:

        ```bash .kamal/secrets
        KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD
        SECRET_KEY_BASE=$MERIDIAN_SECRET_KEY_BASE
        GITHUB_TOKEN=$MERIDIAN_GITHUB_TOKEN
        GITHUB_APP_WEBHOOK_SECRET=$MERIDIAN_GITHUB_APP_WEBHOOK_SECRET
        ```

        ```bash
        export KAMAL_REGISTRY_PASSWORD=...
        export MERIDIAN_SECRET_KEY_BASE=$(openssl rand -hex 64)
        export MERIDIAN_GITHUB_TOKEN=github_pat_...
        export MERIDIAN_GITHUB_APP_WEBHOOK_SECRET=...
        ```
      </Tab>
    </Tabs>

    <Warning>
    Keep `SECRET_KEY_BASE` safe, and never change it. Meridian signs session cookies with it and makes the setup code from it. A new value signs everyone out.
    </Warning>
  </Step>

  <Step title="Deploy Meridian">
    <Tabs>
      <Tab title="Published image">
        Use the published image instead of building one:

        ```bash
        kamal setup --skip-push --version v0.1.0
        ```
      </Tab>
      <Tab title="Your own build">
        With your registry in placeholders 3 and 5, Kamal builds your checkout, pushes the image and deploys it:

        ```bash
        kamal setup
        ```
      </Tab>
    </Tabs>

    `kamal setup` installs Docker on the host if it is missing, starts kamal-proxy and starts Meridian. On first start, Meridian creates its databases. Check that it answers:

    ```bash
    curl https://meridian.example.com/up
    ```

    A `200` response means Meridian is up.
  </Step>

  <Step title="Create your account">
    Open `https://meridian.example.com`. Meridian shows **Welcome to Meridian** and asks for a **Setup code**. The code proves that you run the server. Opening the page writes it to Meridian's log. Read it with either command:

    ```bash
    kamal app logs | grep "setup code"
    kamal app exec 'bin/rails meridian:setup_code'
    ```

    Enter the code, your name, your email and a password of at least 12 characters. Press **Create admin**. Meridian signs you in and opens **Projects**. This is the only account. You can change your name, email and password later under [Settings](/operate/settings).
  </Step>

  <Step title="Add your infra repository">
    Each infra repository you add is a [project](/reference/glossary#project). On **Projects**, press **Add project** and fill in the form:

    | Field | Value |
    | --- | --- |
    | **Name** | Any name, such as `Production`. |
    | **Repository** | The infra repository as `owner/name`, such as `acme/infra`. |
    | **Branch** | The branch that holds what should run. The default is `main`. |
    | **GitHub App installation ID** | The number from step 1. Leave it blank with a token. |
    | **Config paths** | File patterns for your Kamal configs, comma-separated. The default is `config/deploy*.yml`. Use `kamal/*.yml` for one config per app in a `kamal/` folder. |

    Leave **Let admins commit changes directly instead of opening pull requests** off. Turn it on only if you want new apps and the CI workflow committed straight to the branch.

    Save, and Meridian reads the repository. Each config and [destination](/reference/glossary#destination) becomes an [app](/reference/glossary#app) on the board. A config that fails to parse shows under **Parse errors**, with its file and line. See [apps and destinations](/concepts/apps-and-destinations).
  </Step>

  <Step title="Add the CI workflow">
    On the project's page, press **Add CI workflow**. Meridian opens a pull request that adds the [CI workflow](/reference/glossary#ci-workflow), `.github/workflows/meridian-deploy.yml`. It runs `kamal deploy` each time a [version file](/reference/glossary#version-file) changes.

    Before you merge it, add these repository secrets to the infra repository, on Meridian's [Secrets](/guides/secrets) page or in GitHub:

    - `KAMAL_SSH_PRIVATE_KEY`, a private key that can SSH to your app servers.
    - `KAMAL_REGISTRY_PASSWORD`, a token that can pull your app images.
    - Every secret your configs list under `env.secret`.

    The workflow turns every repository secret into an environment variable. So your infra repository's `.kamal/secrets` reads each one as `$NAME`:

    ```bash .kamal/secrets
    KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD
    DATABASE_URL=$DATABASE_URL
    ```

    The workflow runs on `ubuntu-latest`. If GitHub's machines can't reach your servers over SSH, set the repository variable `MERIDIAN_RUNS_ON` to the label of your own runner. See [CI workflow](/reference/ci-workflow).
  </Step>

  <Step title="Put the agent on your servers">
    The [agent](/reference/glossary#agent) is a small read-only program on each server that tells Meridian what runs there. Until an agent reports, every cell on the board shows as **unknown**.

    Open **Agents** in Meridian. It shows two Kamal accessories, with your Meridian URL filled in. Add them to a Kamal config that reaches every host.

    1. Give the token a **Label**, such as `web-1`, press **Create token** and copy it. Meridian shows it once.
    2. Put the token in that config's `.kamal/secrets` as `MERIDIAN_TOKEN`.
    3. In the accessories, replace `SERVICE` with the config's service. Replace `REGION` and `PROVIDER` with your own labels.
    4. Create the agent's Docker network once on every host:

       ```bash
       kamal server exec "docker network inspect meridian >/dev/null 2>&1 || docker network create meridian"
       ```

    5. Start the accessories:

       ```bash
       kamal accessory boot meridian_docker
       kamal accessory boot meridian_agent
       ```

    Within 15 seconds, the server's cells change from **unknown** to their real state. [Install the agent](/guides/agent) covers tokens, labels and every setting.
  </Step>
</Steps>

## Check the install

Open **Settings**. The **Connections** card shows how Meridian reaches GitHub:

| Connection | Expect |
| --- | --- |
| GitHub | **App 123456**, or **Token** with a personal access token |
| Webhooks | **On**. **Off** means `GITHUB_APP_WEBHOOK_SECRET` is unset, and Meridian checks GitHub every 30 seconds instead. |
| Kamal | The Kamal version Meridian parses configs with, `2.12.0` |

The board's **Getting started** list ticks off three steps as you go. They are a project connected, an agent reporting and a first deploy. The list goes away when all three are done.
