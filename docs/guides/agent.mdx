`meridian-agent` runs on each server and tells Meridian what is running there. It reads Docker through a read-only proxy, posts a snapshot of the host's Kamal containers every 15 seconds, and keeps one outbound WebSocket open for live stats and logs. It never starts, stops or changes anything, and it only connects out, so it works behind NAT and firewalls.

Without agents, the board knows only what Git says. Every cell stays **Unknown**.

## What it sends

- **Kamal containers only.** It recognises them by the labels Kamal sets, `service`, `role` and `destination`, and by the name `kamal-proxy`. It takes the version from the container name, as Kamal does. Every other container is ignored and never inspected.
- **Name, image, labels, state, health and start time** of each one. Never environment variables, commands, entrypoints or mounts, which can hold secrets.
- **The host's machine ID, hostname, labels, and agent version.**
- **Live numbers and log lines**, only while someone looks, and logs only if you turn them on.

The payloads, leases and limits are in [Agent protocol](/reference/agent-protocol).

## Before you start

- A Kamal config whose `servers` cover every host you want to watch. The agent runs as two accessories of that config.
- `MERIDIAN_URL` is an address each host can reach, such as `https://meridian.example.com`. Your proxy must pass WebSockets through to Meridian's `/cable`. kamal-proxy and Thruster both do.
- You are an admin, to create the token. Anyone can open **Agents** and read the steps.

## Install with Kamal

<Steps>
  <Step title="Create a token">
    Open **Agents** under **Manage**. Under **Connect a server**, type a **Label**, such as `web-1`. Tick **Fleet token, shared by many servers** if one token will serve several hosts. See [One token per server, or one for the fleet](#one-token-per-server-or-one-for-the-fleet). Click **Create token**.

    Copy the token from **Copy this token now**. Meridian keeps only a digest and can't show it again.
  </Step>
  <Step title="Give Kamal the token">
    Add the token to the secrets file Kamal reads for the config, such as `.kamal/secrets`:

    ```bash .kamal/secrets
    MERIDIAN_TOKEN=$MERIDIAN_TOKEN
    ```

    Then export `MERIDIAN_TOKEN` in the shell you run Kamal from, or read it from your password manager in that line.
  </Step>
  <Step title="Add the two accessories">
    Copy the accessories from **Install** on the **Agents** page. It fills in your `MERIDIAN_URL`. The same text is in `templates/kamal/agent-accessories.yml`. Put them under `accessories:`, and replace `SERVICE` with the config's `service`, and `REGION` and `PROVIDER` with your labels.

    ```yaml config/deploy.yml
    accessories:
      meridian_docker:
        # Read-only Docker API: only GETs under /containers (list, inspect
        # and, while someone is looking, stats and logs).
        image: tecnativa/docker-socket-proxy:v0.4.1
        roles: [ web ]
        network: meridian
        env:
          clear:
            CONTAINERS: 1
            POST: 0
        volumes:
          - /var/run/docker.sock:/var/run/docker.sock:ro

      meridian_agent:
        image: ghcr.io/bigint/meridian-agent:v0.1.0
        roles: [ web ]
        network: meridian
        env:
          clear:
            MERIDIAN_URL: https://meridian.example.com
            DOCKER_HOST: tcp://shop-meridian_docker:2375
            MERIDIAN_LABELS: region=sgp,provider=ovh
            MERIDIAN_LOGS: 1
          secret:
            - MERIDIAN_TOKEN
        volumes:
          - /etc/machine-id:/host/etc/machine-id:ro
          - /etc/hostname:/host/etc/hostname:ro
          - /proc:/host/proc:ro
    ```
  </Step>
  <Step title="Create the network">
    Once per host, create the `meridian` Docker network the two accessories share. Kamal creates only its own `kamal` network.

    ```bash
    kamal server exec "docker network inspect meridian >/dev/null 2>&1 || docker network create meridian"
    ```
  </Step>
  <Step title="Boot them">
    ```bash
    kamal accessory boot meridian_docker
    kamal accessory boot meridian_agent
    ```

    `kamal deploy` never starts accessories, so this step is always by hand.
  </Step>
  <Step title="Check it reports">
    On **Agents**, the token's **Last used** turns to a time, and a per-server token shows its server. The server's page says **Reporting**, and the board fills in its cells within one interval, 15 seconds by default.
  </Step>
</Steps>

### What each accessory does

- **`meridian_docker`** is [`tecnativa/docker-socket-proxy`](https://github.com/Tecnativa/docker-socket-proxy) with `CONTAINERS=1` and `POST=0`. It allows `GET` requests under `/containers` and nothing else. The agent talks to Docker only through it, so even an agent someone has taken over can't start, stop or exec into containers. Mounting the socket `:ro` alone doesn't make the API read-only.
- **`meridian_agent`** is the agent, a static Go binary of about 3.5 MB on a distroless image, running as `nonroot`. It reads the host's machine ID and hostname from the two mounted files, and the host's CPU, memory and load from `/proc` for live stats. Leave the `/proc` mount out, and the server page shows per-container numbers only.

<Warning>
Both accessories run on their own `meridian` network, never on Kamal's `kamal` network where your apps and previews run. The socket proxy answers anyone who can reach port 2375 with every container's environment, files and logs. Never publish its port on the host.
</Warning>

The agent still reaches `MERIDIAN_URL` from the `meridian` network, as long as that is an address the host itself can reach, such as a public or private hostname or an IP address. The name of a container on the `kamal` network doesn't work from there.

## One token per server, or one for the fleet

| | Per-server token | Fleet token |
| --- | --- | --- |
| Binds to | The first machine that uses it | Nothing. Each server is known by its machine ID. |
| Another machine uses it | Refused with `422`: `This token belongs to another server. Give each server its own token, or use a fleet token`. The agent logs the refusal. | Accepted, as its own server |
| Revoking it silences | One server | Every server that uses it |
| **Server** column on **Agents** | The server, or `binds on first contact` | `many` |

Kamal gives every host of an accessory the same secret. With the template's `roles: [ web ]` on several hosts, use a fleet token, or one accessory per host with its own token.

A machine rebuilt with a new machine ID can keep a per-server token. Once the old machine has been silent for 10 minutes, the new one takes the server back.

To revoke a token, click **Revoke** in its row on **Agents** and confirm. Meridian refuses its snapshots from then on, and hangs up its WebSocket at once.

## Matching servers to Git

Git names a server by the host Kamal connects to, such as `web-1.example.com` or an IP address. The agent reports the machine's own hostname. Meridian matches them in this order:

1. The exact hostname.
2. The first DNS label, when only one server has it. `web-1` matches `web-1.example.com`.
3. An IP address, matched only whole.

If the agent reported before Git listed the host, it made a server of its own. Git's name takes that server over when it is the only one sharing the host's first DNS label.

When nothing matches, set `MERIDIAN_HOSTNAME` on the agent to the name in your config:

```yaml
env:
  clear:
    MERIDIAN_HOSTNAME: web-1.example.com
```

Then reboot the agent. Servers whose agent never reported are listed under **Silent agents** on the **Agents** page.

## Labels and map location

`MERIDIAN_LABELS` sets the labels the board filters and groups by, as comma-separated `key=value` pairs. Use any keys you like. Four have a use in Meridian:

| Label | Used for |
| --- | --- |
| `region` | Board filter and grouping, map place names, and the server's place |
| `provider` | Board filter and grouping |
| `role` | Board filter and grouping, and label selectors for new apps and previews |
| `city` | Map place names, and the server's place |

Add `lat` and `lng`, in decimal degrees, to put the server on the map. `latitude`, `longitude` and `lon` work too.

```yaml
MERIDIAN_LABELS: region=sgp,provider=ovh,role=web,city=Singapore,lat=1.35,lng=103.82
```

An admin can also set a location on the server's page, under **Location on the map**. An agent that reports `lat` and `lng` overrides it on its next snapshot. See [The map](/guides/board-and-map#the-map).

## Settings

The agent reads its settings from the environment. These are the ones you are likely to change:

| Variable | Default | What it does |
| --- | --- | --- |
| `MERIDIAN_URL` | required | Meridian's base URL. |
| `MERIDIAN_TOKEN` | required | The token from **Agents**. |
| `MERIDIAN_LABELS` | none | Labels, such as `region=sgp,provider=ovh`. |
| `MERIDIAN_INTERVAL` | `15s` | Time between snapshots, at least `1s`, with up to 20% jitter. Meridian calls a server stale after three intervals, and never sooner than 45 seconds. |
| `MERIDIAN_LOGS` | off | `1` or `true` lets deployers read Kamal containers' logs and traffic. |
| `MERIDIAN_LIVE` | on | `0` or `false` turns the WebSocket off: no live stats, no logs, snapshots only. |
| `MERIDIAN_HOSTNAME` | the host's `/etc/hostname` | The name the agent reports. |

Every variable, including `DOCKER_HOST` and `MERIDIAN_MACHINE_ID`, is in [Environment](/reference/environment).

To see what the agent would send without sending it, run `meridian-agent -print`. It prints one snapshot and needs no URL or token.

## Upgrade the agent

<Steps>
  <Step title="Change the image tag">
    Set `meridian_agent`'s `image` to the new tag, such as `ghcr.io/bigint/meridian-agent:v0.2.0`.
  </Step>
  <Step title="Reboot the accessory">
    ```bash
    kamal accessory reboot meridian_agent
    ```
  </Step>
  <Step title="Check the version">
    Each server's page shows the version under **Machine**, as **Agent**.
  </Step>
</Steps>

### From a template without `network: meridian`

Older templates put both accessories on the `kamal` network, where app containers could reach the socket proxy. Move them:

<Steps>
  <Step title="Create the network on every host">
    ```bash
    kamal server exec "docker network inspect meridian >/dev/null 2>&1 || docker network create meridian"
    ```
  </Step>
  <Step title="Add the network lines">
    Add `network: meridian` to both `meridian_docker` and `meridian_agent`.
  </Step>
  <Step title="Reboot both">
    ```bash
    kamal accessory reboot meridian_docker
    kamal accessory reboot meridian_agent
    ```
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="The token shows Last used, but the server has no cells">
    Git and the agent name the server differently. Find the agent's server under **Servers**, compare its hostname with the host in your config, and set `MERIDIAN_HOSTNAME` to match. See [Matching servers to Git](#matching-servers-to-git).
  </Accordion>
  <Accordion title="The agent logs a 422">
    A per-server token is in use on a second machine. Create a fleet token, or one token per host.
  </Accordion>
  <Accordion title="The agent logs a 429">
    One token sent more than 120 snapshots a minute, or one machine did with a fleet token, or a fleet token's machines together sent more than 12,000. The agent waits as long as the `Retry-After` header asks, then carries on. Raise `MERIDIAN_INTERVAL` if you set it very low.
  </Accordion>
  <Accordion title="The server page stays at Connecting…">
    The WebSocket doesn't reach Meridian. Check that `MERIDIAN_LIVE` isn't `0`, and that every proxy between the agent and Meridian passes WebSockets through to `/cable`.
  </Accordion>
  <Accordion title="The agent can't reach the socket proxy">
    `DOCKER_HOST` must name the proxy's container, `<service>-meridian_docker`, with the config's real service, on port `2375`. Both accessories must be on the `meridian` network.
  </Accordion>
</AccordionGroup>
