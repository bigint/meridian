The [infra repository](/reference/glossary#infra-repository) is the Git repository that holds your Kamal configs. Meridian reads it on every sync and writes to it for every deploy. This page lists every file and rule involved.

A [project](/reference/glossary#project) is one infra repository added to Meridian.

With the config path `deploy/*.yml`, Meridian sees four apps and one accessories-only config:

| App | Config | Destination | Version file |
| --- | --- | --- | --- |
| `blog` | `deploy/blog.yml` | none | `deploy/blog.version` |
| `web · staging` | `deploy/web.yml` | `staging` | `deploy/web.staging.version` |
| `web · production` | `deploy/web.yml` | `production` | `deploy/web.production.version` |
| `edge` | `deploy/edge.yml` | none | none. It runs only accessories. |

## Files Meridian reads and writes

| File | Meridian reads | Meridian writes |
| --- | --- | --- |
| Configs that match the project's config paths | On every sync | When **New app** creates one, and when **Edit connectors** changes an edge config |
| `<config>.<destination>.yml` | On every sync | When **New app** creates an app with a destination |
| `<config>[.<destination>].version` | Its content and history, whenever it changed | On every deploy and rollback, and when **New app** creates an app |
| `.github/workflows/meridian-deploy.yml` | Only to replace it | When you press **Add CI workflow** |

## Config paths

Config paths tell Meridian which files are [configs](/reference/glossary#config). Each project has a list of them: file patterns (globs), separated by commas. The default is `config/deploy*.yml`.

- Patterns match whole folder names. `*` stops at `/`, and `**` matches across folders.
- Only files that end in `.yml` or `.yaml` count.

**New app** writes a new config at the first pattern with exactly one `*`, with the service name in place of the `*`. It drops any `**/` in that pattern first.

| Config paths | New app `shop` goes to |
| --- | --- |
| `config/deploy*.yml` | `config/deploy-shop.yml` |
| `deploy/*.yml` | `deploy/shop.yml` |
| `deploy/**/*.yml` | `deploy/shop.yml` |

When no pattern has one `*`, **New app** refuses to create the app, because sync would never find its config.

## Destinations

A [destination](/reference/glossary#destination) is a variant of a config, such as `staging` or `production`. A file named `x.<destination>.yml` is the `<destination>` destination of `x.yml`, or of `x.yaml`, when both match the config paths. Kamal reads it with `-d <destination>`, on top of the base config.

- A config with destination files becomes one app per destination. The base config on its own is then not an app.
- Only `.yml` destination files count, as in Kamal. `web.staging.yaml` next to `web.yml` is a config of its own.

## Version files

A [version file](/reference/glossary#version-file) sits next to its config and holds one line: the image tag that CI deploys.

| Config | Destination | Version file |
| --- | --- | --- |
| `deploy/blog.yml` | none | `deploy/blog.version` |
| `deploy/web.yml` | `production` | `deploy/web.production.version` |
| `config/deploy.yaml` | none | `config/deploy.version` |

```text deploy/web.production.version
3f2a9c1e
```

- A version must be a Docker image tag: letters, digits, `_`, `.` and `-`. It can be at most 128 characters, and can't start with `.` or `-`.
- Deploy and Roll back change only this file. CI deploys whatever it holds.
- Each commit that changed the file is a release of the version it wrote. Meridian reads the last 20.
- Without a version file, each commit to the config, or to its destination file, is a release. Its name is the commit's short ID (SHA).
- The board shows an app with no version file as unknown, because there is no version to compare. It also has no **Redeploy**.

See [Versions and releases](/concepts/versions-and-releases).

## Labels

Meridian reads two optional labels from a config's `labels:`:

```yaml deploy/web.yml
labels:
  meridian.kind: node
  meridian.source: acme/web
```

<ResponseField name="meridian.kind" type="string" default="other">
  What the app is built with: `static`, `node`, `rails`, `other` or `accessories`. Any other value, or none, reads as `other`.

  `accessories` marks a config that runs only accessories, such as a Cloudflare Tunnel's edge config. The board leaves it out, and Meridian never deploys, rolls back or redeploys it.
</ResponseField>

<ResponseField name="meridian.source" type="string">
  The repository the app is built from, as `owner/name`. The app's page shows it as **Source**.
</ResponseField>

Git is the record. If you take a label out of the config, Meridian clears it on the next sync.

## Secret names

Meridian lists the secrets each config names, so you can set them on the **Secrets** page. It reads names, never values, from:

- `env.secret`, at the top, under each role in `servers`, and under each accessory.
- `env.tags.<tag>.secret` in each of those.
- `registry.password`, when it is a list.

For `KEY:ALIAS`, Meridian takes `ALIAS`, the name the secret has in the environment. It skips names that start with `GITHUB_`, because GitHub can't store them.

## Commits

Every commit Meridian makes for you ends in a `Meridian-Actor:` line, called a trailer. It holds your name and email address.

<CodeGroup>
```text Deploy
deploy(web-production): 3f2a9c1e

Meridian-Actor: Ada Lovelace <ada@example.com>
```

```text Roll back
rollback(web-production): 1b7d0e44

This reverts commit 9c41f0d2a7e3b8c5d6f1a2b3c4d5e6f7a8b9c0d1.

Meridian-Actor: Ada Lovelace <ada@example.com>
```
</CodeGroup>

- The part in brackets is the service, plus `-<destination>` when the app has one.
- A rollback writes the version the file held before the newest release, and names that release's commit.

Commits made outside Meridian count the same. A `git push` that changes a version file is a deploy, and Meridian shows it as one.

## Proposals

By default, Meridian opens a pull request for these three changes:

| Change | Title | Branch |
| --- | --- | --- |
| New app | `feat(<service>): add <kind> app` | `meridian/new-<service>-<hex>` |
| Add CI workflow | `ci: deploy with Kamal when a version file changes` | `meridian/ci-<hex>` |
| Edit connectors | `feat(<tunnel>): add …; remove … as Cloudflare Tunnel connectors` | `meridian/tunnel-<tunnel>-<hex>` |

`<hex>` is six random hexadecimal characters. Meridian creates the branch from the newest commit on the project's branch. It writes each file as its own commit, with the title and the `Meridian-Actor:` trailer as the message. Then it opens the pull request against the project's branch.

When the project has **Direct commits** on, Meridian commits your change straight to the project's branch, one commit per file. Deploys and rollbacks are always direct commits.

## What Meridian never reads

- `.kamal/secrets`, or any other `.kamal/secrets*` file. The CI workflow passes every repository secret in as an environment variable, and `.kamal/secrets` reads them as `$NAME`.
- `.kamal/hooks`, Dockerfiles, and source code.
- Any file outside the config paths, apart from version files.

Kamal itself parses your configs, in a separate process with an empty environment. See [Security](/operate/security).

<Accordion title="How sync reads the repository">
  On each sync, Meridian lists every path in the tree with its blob SHA, a hash of the file's content. It fetches configs and destination files only when their SHA changed, and reads version files only when they changed.

  GitHub cuts a tree short at about 100,000 files. When that happens, the sync stops with an error, so Meridian never treats a partial tree as whole.
</Accordion>
