The **Secrets** page lists, for each project, the secret names its Kamal configs use. An admin can set or rotate each value there. A value goes straight from the form to the infra repository's encrypted GitHub Actions secrets. Meridian never stores, logs or shows it, and can't read it back.

Everyone can see the names. Only admins can add names and set values. See [Roles](/concepts/roles).

## Where the names come from

On every sync, Meridian lists the secret names in each config, parsed by Kamal:

- `env.secret`, at the top level, under each role in `servers`, and under each accessory.
- `env.tags.<tag>.secret`, for env set per server tag.
- `registry.password`, when it is a list of names.

An aliased name, `KEY:SECRET`, lists the second part. `TUNNEL_TOKEN:CLOUDFLARE_TUNNEL_TOKEN` lists `CLOUDFLARE_TUNNEL_TOKEN`, the name the value is stored under.

```yaml config/deploy.yml
env:
  secret:
    - DATABASE_URL
    - RAILS_MASTER_KEY
registry:
  server: ghcr.io
  username: acme
  password:
    - KAMAL_REGISTRY_PASSWORD
```

This config gives three names. **Used by** shows the apps that use each one.

Meridian never reads `.kamal/secrets` or any other secrets file. Names that GitHub can't store, such as one that starts with `GITHUB_`, are left out, and they don't stop the sync.

A name that sync listed and nobody set goes away when no config uses it anymore. A name that was set through Meridian, or that an admin added by hand, stays, marked `not referenced by any config`.

## Set or rotate a value

<Steps>
  <Step title="Open Secrets">
    Open **Secrets** under **Manage**. Each project has its own table.
  </Step>
  <Step title="Type the value">
    In the **Set or rotate** column of the name's row, type the value. The field hides what you type.
  </Step>
  <Step title="Save it">
    Click **Set**, or **Rotate** for a name that was set before. Meridian says `DATABASE_URL set. Redeploy the apps that use it to pick it up.`
  </Step>
  <Step title="Redeploy">
    Running containers keep the old value until Kamal restarts them. Open each app in **Used by** and click **Redeploy**. See [Redeploy the current version](/guides/deploy#redeploy-the-current-version).
  </Step>
</Steps>

**Last set** shows when the value was last set through Meridian, and by whom. A value set on GitHub directly shows `not set through Meridian`. Meridian can't tell whether GitHub has it.

### How the value travels

Meridian asks GitHub for the repository's Actions public key, seals the value with it (a libsodium sealed box), and sends GitHub the sealed value. Only GitHub can open it. Meridian keeps the time and the person, and never the value. The value isn't saved to a model, written to a log, put on a job queue, or broadcast to other pages.

## Add a name by hand

Add a name before any config uses it, or one that only CI reads.

<Steps>
  <Step title="Open the form">
    Under the project's table, open **Add another name**.
  </Step>
  <Step title="Fill it in">
    Type the **Name**, such as `DATABASE_URL`. Meridian turns it into upper case. It may hold letters, digits and `_`, must not start with a digit or `GITHUB_`, and has at most 128 characters. **Value (optional)** sets it in the same step.
  </Step>
  <Step title="Add it">
    Click **Add**.
  </Step>
</Steps>

Adding and setting allow 20 requests a minute from one IP address.

## How Kamal gets the values

The CI workflow exports every repository secret as an environment variable before it runs Kamal. Kamal reads its secrets files, and each file maps a name to that variable:

```bash .kamal/secrets
KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD
RAILS_MASTER_KEY=$RAILS_MASTER_KEY
DATABASE_URL=$DATABASE_URL
```

Kamal reads `.kamal/secrets-common` for every run. It also reads `.kamal/secrets` for a config without a destination, or `.kamal/secrets.<destination>` for a run with one, such as `.kamal/secrets.production`. A name missing from the files Kamal reads fails the run with `Secret 'DATABASE_URL' not found in ...`.

<Warning>
A preview runs as the destination `pr-<n>`, so Kamal reads `.kamal/secrets-common` and `.kamal/secrets.pr-<n>`, never `.kamal/secrets`. Put the lines your previews need in `.kamal/secrets-common`. See [Previews](/guides/previews).
</Warning>

## The two CI secrets

The workflow itself needs two repository secrets, whatever your configs say. Set both before the first deploy.

| Secret | What it is |
| --- | --- |
| `KAMAL_SSH_PRIVATE_KEY` | The private key CI uses to SSH to your servers. Its public key must be in each server's `authorized_keys` for the user Kamal connects as. |
| `KAMAL_REGISTRY_PASSWORD` | The password or token Kamal logs in to the registry with. The configs Meridian writes name it in `registry.password`. |

`KAMAL_REGISTRY_PASSWORD` shows on the Secrets page once a config uses it. `KAMAL_SSH_PRIVATE_KEY` appears only after you add it by hand. Add it with **Add another name**, or set it on GitHub directly. See [CI workflow](/reference/ci-workflow).
