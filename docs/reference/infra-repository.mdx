A project in Meridian is one Git repository that holds Kamal configs. Meridian reads it on every sync and writes to it for every deploy. This page lists every file and convention involved.

With the config path `deploy/*.yml`, Meridian sees four apps and one accessories-only config:

| App | Config | Destination | Version file |
| --- | --- | --- | --- |
| `blog` | `deploy/blog.yml` | none | `deploy/blog.version` |
| `web · staging` | `deploy/web.yml` | `staging` | `deploy/web.staging.version` |
| `web · production` | `deploy/web.yml` | `production` | `deploy/web.production.version` |
| `edge` | `deploy/edge.yml` | none | none. It runs only accessories. |

`deploy/web.pr-42.yml` is the overlay of a running preview, not an app. See [Preview overlays](#preview-overlays).

## Files Meridian reads and writes

| File | Meridian reads | Meridian writes |
| --- | --- | --- |
| Configs that match the project's config paths | On every sync | When **New app** creates one, and when **Edit connectors** changes an edge config |
| `<config>.<destination>.yml` | On every sync | When **New app** creates an app with a destination |
| `<config>[.<destination>].version` | Its content and history, whenever it changed | On every deploy and rollback, and when **New app** creates an app |
| `<config>.pr-<n>.yml` | Never as a config | When a pull request opens, and deleted when its preview is removed |
| `.github/workflows/meridian-deploy.yml` | Only to replace it | When an admin presses **Add CI workflow** |

## Config paths

Each project has a list of config paths, globs separated by commas. The default is `config/deploy*.yml`. Globs match whole path segments, so `*` stops at `/` and `**` crosses folders. Only files that end in `.yml` or `.yaml` count.

**New app** writes a new config at the first glob with exactly one `*`, with the service name in place of the `*`. A `**/` in that glob is dropped first.

| Config paths | New app `shop` goes to |
| --- | --- |
| `config/deploy*.yml` | `config/deploy-shop.yml` |
| `deploy/*.yml` | `deploy/shop.yml` |
| `deploy/**/*.yml` | `deploy/shop.yml` |

When no glob has one `*`, **New app** refuses the app, because sync would never find its config.

## Destinations

A file named `x.<destination>.yml` is the `<destination>` destination of `x.yml`, or of `x.yaml`, when both match the config paths. Kamal reads it with `-d <destination>` on top of the base config.

- A config with destination files becomes one app per destination. The base config on its own is then not an app.
- Only `.yml` destination files count, as in Kamal. `web.staging.yaml` beside `web.yml` is a config of its own.
- A destination named `pr-<n>` is a preview overlay, never an app.

## Version files

A version file sits next to its config and holds one line: the image tag CI deploys.

| Config | Destination | Version file |
| --- | --- | --- |
| `deploy/blog.yml` | none | `deploy/blog.version` |
| `deploy/web.yml` | `production` | `deploy/web.production.version` |
| `config/deploy.yaml` | none | `config/deploy.version` |

```text deploy/web.production.version
3f2a9c1e
```

- A version must be a Docker image tag: letters, digits, `_`, `.` and `-`, at most 128 characters, and not starting with `.` or `-`.
- Deploy and Roll back change only this file. CI deploys whatever it holds.
- Each commit that changed the file is a release of the version it wrote. Meridian reads the last 20.
- Without a version file, each commit to the config (or to its destination file) is a release named by its short SHA. The board shows such an app as unknown, because there is no version to compare, and it has no **Redeploy**.

See [Versions and releases](/concepts/versions-and-releases).

## Labels

Meridian reads two optional labels from a config's `labels:`:

```yaml deploy/web.yml
labels:
  meridian.kind: node
  meridian.source: acme/web
```

<ResponseField name="meridian.kind" type="string" default="other">
  The app's kind: `static`, `node`, `rails`, `other` or `accessories`. Any other value, or none, reads as `other`. `accessories` marks a config that runs only accessories, such as a Cloudflare Tunnel's edge config. The board leaves it out, and Meridian never deploys, rolls back or redeploys it.
</ResponseField>

<ResponseField name="meridian.source" type="string">
  The app's source repository, as `owner/name`. Pull requests there get previews. Without it, the app has no previews.
</ResponseField>

Git is the record. Taking a label out of the config clears it in Meridian on the next sync.

## Secret names

Meridian lists the secrets each config names, so the Secrets page can set them. It reads names, never values, from:

- `env.secret`, at the top, under each role in `servers`, and under each accessory,
- `env.tags.<tag>.secret` in each of those,
- `registry.password`, when it is a list.

For `KEY:ALIAS`, Meridian takes `ALIAS`, the name the secret has in the environment. Names that start with `GITHUB_` are skipped, because GitHub can't store them.

## Preview overlays

When a pull request opens in an app's source repository, Meridian commits an overlay next to the base config, as the `pr-<n>` destination:

```yaml deploy/web.pr-42.yml
# Preview of acme/web#42. Generated by Meridian.
# Removed when the pull request closes, or on 2026-12-03.
service: web-pr-42
servers:
  web:
  - preview-1.example.com
proxy:
  host: pr-42.web.preview.example.com
```

- The service is `<service>-pr-<n>`, so the preview's containers never collide with the app's.
- Kamal reads the overlay on top of the base config, so the base config's settings still apply. Settings from the app's destination file are copied in, except where and under which name it runs.
- Each role keeps its own `cmd`, `env` and options, and runs on the preview server.
- A config with several destinations gets one preview per pull request.

Meridian deletes the overlay once CI has removed the preview. See [Previews](/guides/previews).

## Commits

Every commit Meridian makes on a person's behalf ends in a `Meridian-Actor:` trailer with their name and email address.

<CodeGroup>
```text Deploy
deploy(web-production): 3f2a9c1e

Meridian-Actor: Ada Lovelace <ada@example.com>
```

```text Roll back
rollback(web-production): 1b7d0e44

This reverts commit 9c41f0d2a7e3b8c5d6f1a2b3c4d5e6f7a8b9c0d1.

Meridian-Actor: Ada Lovelace <ada@example.com>
```

```text Preview
chore(web): preview pr-42
```

```text Preview removed
chore(web): remove preview pr-42
```
</CodeGroup>

The scope is the service, with `-<destination>` when the app has one. A rollback writes the version that the file held before the newest release, and names that release's commit. Preview commits come from webhooks, not from a person, so they carry no trailer.

Commits made outside Meridian count the same. A `git push` that changes a version file is a deploy, and Meridian shows it as one.

## Proposals

Structural changes go through a pull request by default:

| Change | Title | Branch |
| --- | --- | --- |
| New app | `feat(<service>): add <kind> app` | `meridian/new-<service>-<hex>` |
| Add CI workflow | `ci: deploy with Kamal when a version file changes` | `meridian/ci-<hex>` |
| Edit connectors | `feat(<tunnel>): add …; remove … as Cloudflare Tunnel connectors` | `meridian/tunnel-<tunnel>-<hex>` |

`<hex>` is six random hexadecimal characters. Meridian creates the branch from the head of the project's branch, writes each file as its own commit, with the title and the `Meridian-Actor:` trailer as its message, and opens the pull request against the project's branch.

When the project has **Direct commits** on, an admin's change is committed straight to the project's branch instead, one commit per file. Deploys, rollbacks and preview overlays are always direct commits.

## What Meridian never reads

- `.kamal/secrets` and any other `.kamal/secrets*` file. The CI workflow exports every repository secret as an environment variable, and `.kamal/secrets` reads them as `$NAME`.
- `.kamal/hooks`, Dockerfiles, and source code.
- Any file outside the config paths, apart from version files.

Meridian lists every path and blob SHA in the tree on each sync. It fetches the content of configs and destination files only when their SHA changed, and reads version files only when they changed. A tree GitHub cuts short, at about 100,000 files, stops the sync with an error rather than being read as whole.

Configs are parsed by Kamal itself, in a separate process with an empty environment. See [Security](/operate/security).
