# Decisions

These are short entries, newest last. Each records a choice made where the spec was ambiguous. Meridian takes the simplest option that keeps Git as the record.

1. **Configs are parsed in a clean subprocess.** `bin/kamal-parse` runs with an empty environment, a timeout, and a temporary checkout as its working directory. ERB in a Kamal config is arbitrary Ruby from the infra repository, so it must not see Meridian's credentials or memory.
2. **Versions are passed as the placeholder `"0"` while parsing.** This stops Kamal from shelling out to git. Real versions come from releases.
3. **Kamal errors are given line numbers.** Kamal's `ConfigurationError` reports a key path such as `servers/web/hosts`. Meridian walks the YAML node tree to find that key's line, so every error renders as `file:line`.
4. **The infra repository is read through the API, never cloned.** Meridian uses the tree API plus blob fetches by SHA, and caches blobs by SHA, so only changed files are downloaded.
5. **The release reference is a version file.** Kamal has no version key in its YAML. Meridian therefore writes a one-line file next to the config, `<config>.version` or `<config>.<destination>.version`, for example `config/deploy.production.version` beside `config/deploy.yml`, and the CI workflow passes `--version "$(cat …)"`. Releases are the commits that touched that file. Without one, a release is the latest commit to the config, with its short SHA as the version. The spec's other modes (image tag, build argument) are deferred, and nothing is built for them yet.
6. **An app is one config plus one destination.** `config/deploy.yml` with `deploy.staging.yml` and `deploy.production.yml` produces two apps. A config with no destination files produces one.
7. **A server's identity is its machine id.** The agent sends `/etc/machine-id` (or `MERIDIAN_MACHINE_ID`). Before any agent reports, Git hostnames create placeholder servers, which the first agent that reports a matching hostname claims.
8. **A preview overlay sits next to its base config.** It is `<config base>.pr-<n>.yml`, because Kamal resolves destination files as siblings of `-c`.
9. **kamal-proxy routes are read from the state file in its volume.** Reporting them is opt-in. Meridian never uses `docker exec`.
10. **Board broadcasts are throttled with Solid Cache.** A `write(unless_exist: true, expires_in: 1.second)` key per board group decides whether a refresh broadcast is enqueued, so there are no timers and no extra infrastructure.
11. **Per-server deploy progress is read from agents, not stored.** Kamal deploys every host in one CI job, so CI can't report per-server progress. A deploy is done on a server when its agent reports the target version running there. `Deploy` therefore has no `per_server` column.
12. **Deploys and rollbacks are always direct commits.** They change one line, so they go straight to the default branch. The project's pull-request setting applies only to structural changes: new apps, the CI workflow and preview setup.
13. **A rollback reverts the newest release only.** The version file is restored to its content at that release commit's parent. Meridian checks with Git that the release is still the newest commit to the version file, so a change it hasn't synced yet is never reverted past; if the file didn't exist at the parent there is nothing to roll back to. Rolling back an older release is the same as deploying its version, which the Deploy form already does.
14. **CI is linked to apps by commit SHA.** A `workflow_run` webhook from the deploy workflow is matched to apps through the releases (or Meridian-made deploys) at its `head_sha`; runs of other workflows are ignored. The workflow therefore needs no knowledge of Meridian.
15. **An app's kind and source repository are Docker labels in its config.** `labels: { meridian.kind: node, meridian.source: acme/shop }` keeps them in Git, where sync reads them back. As a side effect they are visible on the containers. A YAML comment couldn't be parsed back, and a database column would hold data that isn't in Git.
16. **Generated configs are validated by Kamal before they are proposed.** A pull request Kamal would reject is never opened.
17. **Secret names come from configs, not from `.kamal/secrets` files.** Those files can contain literal values in some repositories, so Meridian never reads them.
18. **Redeploy is a `workflow_dispatch`.** Rotating a secret doesn't change any file, so there is nothing to commit. Meridian asks the CI workflow to run again for the version the version file holds at that moment, and CI still runs Kamal. An app without a version file has no version to give Kamal, so it can't be redeployed. The dispatch is recorded as an Event.
19. **Preview overlays are direct commits, not pull requests.** They live only as long as their pull request, and a pull request per preview would bury the real changes.
20. **Preview runs are matched by run name.** The workflow names dispatched runs `<command> <config> <destination>`, because `workflow_run` webhooks don't carry inputs.
21. **A preview inherits its app's destination file**, minus `service`, `servers` and the proxy host, so settings such as `app_port` carry over. The base config is shared through Kamal's own merge.
22. **Tailwind replaces hand-written CSS.** This supersedes the spec's "no Tailwind" and "no build step". `tailwindcss-rails` ships Tailwind 4 as a standalone binary, so there is still no Node. It builds before `test:prepare` and `assets:precompile`, so CI and the Docker image need no extra step. The theme is semantic tokens redefined for dark mode, so views never use `dark:` variants.
23. **Views are built from ViewComponent components, browsed in Lookbook.** A component is a Ruby class with a template, so it can be unit-tested and previewed in every state. Lookbook is mounted at `/lookbook` in development only; it turns off CSP for its own pages, and the app keeps its strict CSP.
24. **A left sidebar replaces the central menu.** The main places stay visible, and the search box finds any app, server or project. On phones the same sidebar is a native `popover` drawer, so it needs no JavaScript.
25. **The Inspector layout, picked from three mockups.** Console (dark and dense), Paper (light and calm) and Inspector were drawn side by side before any code changed. Inspector won: a grid where every cell shows the version actually running, and a side panel for the app you click. The panel is a Turbo Frame, so selecting an app swaps only the panel and the URL (`?inspect=`) keeps the choice across refreshes. Navigation became an icon rail with a top bar for search, which gives the grid the width it needs. The board now groups servers by region whenever they span more than one region, not only above 30 servers.
26. **Map dots are SVG links that Turbo visits through a small Stimulus controller.** Turbo reads `link.href` as a string, but inside an `<svg>` it is an `SVGAnimatedString`, so Turbo threw on every click and the browser fell back to a full reload. `svg_link_controller.js` handles the click and calls `Turbo.visit`. Picking a place is a whole-page visit, not a frame, because the ring, the names and the table highlight move with the panel.
27. **The sidebar collapses with a toggle, picked from three mockups.** Toggle (« and »), Peek (a rail that slides out on hover) and Sections (folding groups and recent apps) were drawn first; the toggle won for being predictable. The state is a `sidebar` cookie rather than local storage so the server renders the right width and the page never jumps; it is a display preference, not a setting, so it stays per browser.
28. **Back to vanilla: plain CSS, partials and helpers, no build step.** This reverses 22 and 23 and restores the spec's "no Tailwind, no build step, no component libraries". Tailwind and ViewComponent worked, but they bent the code around them: about 200 arbitrary-value and group variants, `!important` overrides, a form builder that injected class strings, components that couldn't see the controller's form builder, and link-building lambdas passed into components. Meridian now follows how 37signals builds Rails apps: one small CSS file per concern with cascade layers, nesting and custom properties; `light-dark()` for themes; ERB partials and helpers; inputs styled by element. Lookbook went with ViewComponent; helpers and partials are covered by helper and integration tests instead.
29. **The theme is a per-browser cookie, not a user setting.** System, Light or Dark, from the account menu. Like the sidebar, it is a display preference of the device in front of you, and a cookie lets the server render the right theme on the first byte. With `light-dark()` the switch is one attribute on `<html>`; no colour is defined twice.
30. **Live stats ride a WebSocket the agent opens to ActionCable.** A page needs numbers within a second of opening, and a 15-second snapshot can't do that, so Meridian needs a way to reach the agent without connecting in. Long-polling would hold a Puma thread per agent (500 at our target), while ActionCable already holds idle sockets cheaply and is in the stack. The agent stays standard-library Go: it upgrades with `net/http` and frames WebSocket messages itself. Snapshots stay HTTP POSTs; the socket carries only watch leases down and stats frames up.
31. **Stats stream only while someone watches, under a lease.** Streaming Docker stats from every container on 500 servers to Meridian all the time would cost dockerd and SQLite for numbers nobody reads. A page subscribes, Meridian sends the agent "stream for 30 seconds" (relative, so host clocks don't matter) and renews it every 10 seconds while the page is open, throttled to one lease message per server per 5 seconds however many people watch. A closed laptop sends no renewals, so the agent stops on its own. Frames are relayed, never stored; history is a separate, later decision.
32. **Live logs ride the same line, opt-in, Kamal-only, for deployers.** Logs can hold secrets, which the agent otherwise never sends, so three locks apply. The agent tails nothing without `MERIDIAN_LOGS=1`. It checks every container it is asked for against Kamal's labels itself, not trusting Meridian. Only users who can deploy may open logs, and each viewing is an `Event`. Tailing uses the stats lease, per container, so nothing streams unwatched. Lines are relayed, never stored; Solid Cable's message retention drops from a day to a minute so they don't linger in its table. An app's logs merge every server it runs on into one timeline, ordered by Docker's timestamps.
33. **One Cloudflare Tunnel per project, from Git, and Meridian never calls Cloudflare's API.** A tunnel serves every app: an accessories-only config (`deploy/edge.yml`, labelled `meridian.kind: accessories`, which the board leaves out and Meridian never deploys) runs one `cloudflared` connector per server, all reading one token secret, and the tunnel routes each hostname to `http://kamal-proxy:80`. Cloudflare sends a request to whichever connector is nearest, so the rule that makes this safe is that every connector's server runs every app the tunnel serves; that is how production runs (every server runs every site), and it is what the Tunnels page checks from Git. A tunnel per app was tried first and dropped: it multiplied tunnels, tokens and connectors to work around apps spread unevenly, where the honest fix is to run them on the connector servers. The tunnel, its routes and its token are made in Cloudflare by a person; calling the API would need a credential that can change DNS, which breaks "Git is the record" and "Secrets are write-only". Preview hostnames can be flat, `pr-<n>-<app>.<domain>`, as an opt-in account setting, because Cloudflare's free certificate covers one level below the domain; nested stays the default so existing DNS keeps working.
34. **An app's traffic is kamal-proxy's logs, filtered by Meridian.** kamal-proxy already logs every request as JSON, with the service it routed to and the container that answered, so traffic needs no new collector: the Traffic page tails `kamal-proxy` on each of the app's servers with the live-logs lease and its locks. Meridian, not the agent, drops other apps' lines, as each batch arrives and only while someone reads that app's traffic. The agent follows a container once however many people read it, so filtering there would mean one stream per filter; and the agent stays a dumb, read-only pipe. Lines are relayed, never stored.
35. **Agents don't report kamal-proxy routes.** This reverses 9. The agent read the state file and sent `proxy_routes`, but nothing in Meridian ever used them: Git says which hosts an app should answer, and Traffic reads kamal-proxy's logs (34). The feature asked for a root agent and an extra volume for nothing, so it is gone, and `MERIDIAN_PROXY_STATE` is ignored. The research stays in [architecture.md](architecture.md#kamal-proxy-routes-read-only) in case routes are ever worth showing.
