The [CI workflow](/reference/glossary#ci-workflow) is the GitHub Actions file `.github/workflows/meridian-deploy.yml` in your infra repository. It runs Kamal for Meridian. Every deploy, rollback and redeploy goes through this one file.

Meridian never runs Kamal against your servers. It commits a version file, or asks GitHub to start this workflow. The workflow then runs `kamal deploy`.

## Add or update it

On the project's page, press **Add CI workflow**. Meridian opens a pull request with the file, or commits it when the project has **Direct commits** on.

Meridian fills in two values. The branch in `on.push.branches` is the project's branch. The Kamal version is the one Meridian reads configs with, `2.12.0` in this release.

Before you merge it, add two repository secrets under **Settings → Secrets and variables → Actions**:

- `KAMAL_SSH_PRIVATE_KEY`, the key Kamal uses to connect to your servers over SSH.
- `KAMAL_REGISTRY_PASSWORD`, the password that your configs' `registry.password` names.

Add the secrets your configs use too, from Meridian's **Secrets** page. See [Secrets](/guides/secrets).

When a Meridian release changes the template, press **Add CI workflow** again to get the new file. The [changelog](/changelog) says when.

## The whole file

This is the file Meridian adds for a project on `main`:

```yaml .github/workflows/meridian-deploy.yml
# Deploys with Kamal when a version file changes. Added by Meridian; edit freely.
#
# Meridian never deploys itself: it commits `<config>.version` (or
# `<config>.<destination>.version`), and this workflow runs `kamal deploy`.
# Redeploys use the same workflow through workflow_dispatch.
name: Meridian deploy
# Meridian matches redeploy runs by this name: "<command> <config> <destination>".
run-name: ${{ github.event_name == 'workflow_dispatch' && format('{0} {1} {2}', inputs.command, inputs.config, inputs.destination) || github.event.head_commit.message }}

on:
  push:
    branches: [ main ]
    paths: [ "**/*.version" ]
  workflow_dispatch:
    inputs:
      config:
        description: Kamal config path, e.g. config/deploy.yml
        required: true
      destination:
        description: Kamal destination (optional)
        required: false
      version:
        description: Version to deploy
        required: false
      command:
        description: Kamal command (deploy)
        required: true
        default: deploy

jobs:
  plan:
    # Set the repository variable MERIDIAN_RUNS_ON to use your own runner
    # (e.g. "self-hosted") when the servers aren't reachable from GitHub.
    runs-on: ${{ vars.MERIDIAN_RUNS_ON || 'ubuntu-latest' }}
    outputs:
      matrix: ${{ steps.plan.outputs.matrix }}
    steps:
      # The whole history, so a push of several commits can be diffed from
      # the commit before the push.
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
      - id: plan
        shell: bash
        run: |
          set -euo pipefail
          if [ "${{ github.event_name }}" = "workflow_dispatch" ]; then
            jq -nc --arg c "${{ inputs.config }}" --arg d "${{ inputs.destination }}" --arg v "${{ inputs.version }}" --arg k "${{ inputs.command }}" \
              '[{config:$c, destination:$d, version:$v, command:$k}]' > matrix.json
          else
            # Every version file the push changed, from the commit before it
            # (the parent when that commit is unknown, e.g. a new branch).
            before="${{ github.event.before }}"
            if ! git cat-file -e "$before^{commit}" 2>/dev/null; then
              before="$(git rev-parse -q --verify HEAD~1 || git hash-object -t tree /dev/null)"
            fi
            : > rows
            git diff --name-only "$before" HEAD -- '*.version' | while IFS= read -r file; do
              [ -f "$file" ] || continue
              # <config>.<destination>.version when <config>.yml exists,
              # otherwise <config>.version; configs may end in .yml or .yaml.
              stem="${file%.version}" name="${stem##*/}" config="" destination=""
              for ext in yml yaml; do
                if [ "$name" != "${name%.*}" ] && [ -f "${stem%.*}.$ext" ]; then
                  config="${stem%.*}.$ext" destination="${stem##*.}"; break
                fi
              done
              for ext in yml yaml; do
                if [ -z "$config" ] && [ -f "$stem.$ext" ]; then config="$stem.$ext"; fi
              done
              if [ -z "$config" ]; then echo "::warning::No Kamal config for $file"; continue; fi
              jq -nc --arg c "$config" --arg d "$destination" --arg v "$(tr -d '[:space:]' < "$file")" \
                '{config:$c, destination:$d, version:$v, command:"deploy"}' >> rows
            done
            jq -sc '.' rows > matrix.json
          fi
          echo "matrix=$(cat matrix.json)" >> "$GITHUB_OUTPUT"

  kamal:
    needs: plan
    if: needs.plan.outputs.matrix != '[]'
    runs-on: ${{ vars.MERIDIAN_RUNS_ON || 'ubuntu-latest' }}
    strategy:
      fail-fast: false
      matrix:
        include: ${{ fromJson(needs.plan.outputs.matrix) }}
    name: ${{ matrix.command }} ${{ matrix.config }} ${{ matrix.destination }}
    # One Kamal run per app at a time, whether a push or a dispatch started it.
    # Runs for different apps never wait on or cancel each other; a newer
    # pending run for the same app replaces an older pending one.
    concurrency:
      group: meridian-${{ matrix.config }}-${{ matrix.destination }}
      cancel-in-progress: false
    steps:
      - uses: actions/checkout@v6
      - uses: ruby/setup-ruby@v1
        if: runner.environment == 'github-hosted'
        with:
          ruby-version: "3.4"
      - run: kamal version 2>/dev/null | grep -qx "2.12.0" || gem install kamal -v 2.12.0 --no-document
      - uses: webfactory/ssh-agent@v0.9.0
        with:
          ssh-private-key: ${{ secrets.KAMAL_SSH_PRIVATE_KEY }}
      # Every repository secret becomes an environment variable, so
      # .kamal/secrets can read it as $NAME. Meridian's Secrets page sets them.
      - name: Export secrets
        shell: bash
        env:
          SECRETS: ${{ toJSON(secrets) }}
        run: |
          echo "$SECRETS" | jq -r 'to_entries[] | select(.key != "github_token") | "\(.key)<<MERIDIAN_EOF\n\(.value)\nMERIDIAN_EOF"' >> "$GITHUB_ENV"
      - name: Kamal
        shell: bash
        run: |
          set -euo pipefail
          args=(-c "${{ matrix.config }}")
          [ -n "${{ matrix.destination }}" ] && args+=(-d "${{ matrix.destination }}")
          kamal deploy "${args[@]}" --version "${{ matrix.version }}" --skip-push
```

The comment at the top says "edit freely", and you can. Keep the parts listed in [What Meridian relies on](#what-meridian-relies-on).

## Triggers

Two triggers start the workflow: `push` and `workflow_dispatch`.

<ResponseField name="push" type="trigger">
  A push to the project's branch that changes a `*.version` file anywhere in the repository. Deploy and Roll back in Meridian are pushes like this. So is any commit you push yourself.
</ResponseField>

<ResponseField name="workflow_dispatch" type="trigger">
  A run that Meridian starts through GitHub's API, for a redeploy. GitHub calls this a dispatch. You can also start one yourself from the **Actions** tab.
</ResponseField>

### Inputs

A dispatched run takes these four inputs.

<ResponseField name="config" type="string" required>
  The Kamal config path, for example `deploy/web.yml`.
</ResponseField>

<ResponseField name="destination" type="string">
  The Kamal destination, for example `production`. Leave it empty for an app without one.
</ResponseField>

<ResponseField name="version" type="string">
  The image tag to deploy. For a redeploy, it is the version in the version file.
</ResponseField>

<ResponseField name="command" type="string" default="deploy" required>
  `deploy` runs `kamal deploy`. Meridian sends no other command.
</ResponseField>

## Run name

Meridian reads the `run-name` line to tell what each run is for, so keep its format.

| Started by | Run name | Example |
| --- | --- | --- |
| `workflow_dispatch` | `<command> <config> <destination>` | `deploy deploy/web.yml production` |
| `push` | The message of the newest commit in the push | `deploy(web-production): 3f2a9c1e` |

A dispatched `deploy` run is a redeploy of the app with that config and destination.

For a push run, Meridian looks at its newest commit instead, and finds the deploy that made that commit.

## The plan job

The `plan` job turns the trigger into a list of Kamal runs. GitHub calls this list a matrix.

- **On a dispatch**, the list has one row, built from the four inputs.
- **On a push**, it has one row per version file the push changed. `plan` compares against the commit before the push. When that commit is unknown, as on a new branch, it starts from the parent commit.
- `plan` skips version files that the push deleted.

For each version file, `plan` finds the config:

1. `<config>.<destination>.version` belongs to `<config>.yml` or `<config>.yaml`, with destination `<destination>`, when that config exists.
2. Otherwise, `<stem>.version` belongs to `<stem>.yml` or `<stem>.yaml`, with no destination.
3. If it finds no config, the run logs the warning `No Kamal config for <file>` and skips the file.

The version is the file's content with whitespace removed. If the list is empty, the `kamal` job is skipped.

## The kamal job

The `kamal` job runs once per row, named `<command> <config> <destination>`. `fail-fast: false` keeps the other apps going when one fails.

| Step | What it does |
| --- | --- |
| `actions/checkout@v6` | Checks out the commit the run is for. |
| `ruby/setup-ruby@v1` | Installs Ruby 3.4, on GitHub-hosted runners only. |
| Install Kamal | Installs the pinned Kamal version, unless that exact version is already there. |
| `webfactory/ssh-agent@v0.9.0` | Loads `KAMAL_SSH_PRIVATE_KEY` into an SSH agent. |
| Export secrets | Turns every repository secret into an environment variable. |
| Kamal | Runs `kamal deploy -c <config> [-d <destination>] --version <version> --skip-push`. |

`--skip-push` means CI never builds an image. The source repository's own CI pushes the image, and Kamal pulls it on each server.

### Concurrency

```yaml
concurrency:
  group: meridian-${{ matrix.config }}-${{ matrix.destination }}
  cancel-in-progress: false
```

This block makes Kamal run one at a time per app, whether a push or a dispatch started it.

- GitHub never cancels a running deploy.
- Runs for different apps never wait for each other.
- While one run for an app is going, GitHub keeps only the newest waiting run for that app. It cancels the older waiting one.

### Secrets

```bash
echo "$SECRETS" | jq -r 'to_entries[] | select(.key != "github_token") | "\(.key)<<MERIDIAN_EOF\n\(.value)\nMERIDIAN_EOF"' >> "$GITHUB_ENV"
```

This line turns every repository secret except `github_token` into an environment variable with the same name, for the Kamal step. The `MERIDIAN_EOF` marker keeps values with several lines, such as a key, whole. `.kamal/secrets` then reads each one as `$NAME`:

```bash .kamal/secrets
KAMAL_REGISTRY_PASSWORD=$KAMAL_REGISTRY_PASSWORD
RAILS_MASTER_KEY=$RAILS_MASTER_KEY
```

The values you set on Meridian's **Secrets** page are repository secrets, so they reach Kamal this way.

## Self-hosted runners

GitHub's hosted runners reach your servers over the public internet. When your servers are on a private network, run the workflow on a runner that can reach them. Set the repository variable `MERIDIAN_RUNS_ON` under **Settings → Secrets and variables → Actions → Variables**:

```text
MERIDIAN_RUNS_ON = self-hosted
```

Both jobs use it. Without it, they use `ubuntu-latest`.

The runner needs `bash`, `git`, `jq`, `ssh-agent`, and Ruby with `gem`. The workflow skips `ruby/setup-ruby` on self-hosted runners, so the Ruby on the runner's `PATH` installs Kamal.

## What Meridian relies on

You can change anything else in the file, but keep these:

- The file name, `meridian-deploy.yml`. Meridian starts the workflow by this name, and only its runs move deploys along.
- The `run-name` expression. Meridian reads it to track redeploys.
- The four inputs, with these names. Meridian sends `config`, `destination`, `version` and `command`.
- The `push` trigger on `**/*.version` and the project's branch. Deploy and Roll back are commits there.

When the file is missing from the project's branch, a redeploy fails with this error: `<repo> has no meridian-deploy.yml workflow on <branch>: add the CI workflow first`.
