Meridian reads and writes your repositories as a GitHub App. The App keeps Meridian to the repositories you install it on, with only the permissions below. For a first-time walk-through, see [Install](/install).

## App settings

| Setting | Value |
| --- | --- |
| Homepage URL | Your Meridian, for example `https://meridian.example.com` |
| Webhook | Not active. Meridian polls GitHub instead. |
| Where can this App be installed | Only on this account |

After you create the App, note its **App ID** and generate a **private key**. They become `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY`. See [Environment variables](/reference/environment#github).

## Where to install it

Install the App on the [infra repository](/reference/glossary#infra-repository), which holds your Kamal configs, and no others. There Meridian reads configs, commits version files, opens pull requests, starts the deploy workflow and sets Actions secrets.

## Installation ID

Each project in Meridian names the installation it reads through. After you install the App, GitHub takes you to a URL that ends in the installation ID:

```text
https://github.com/settings/installations/12345678
https://github.com/organizations/acme/settings/installations/12345678
```

Enter that number as **GitHub App installation ID** when you add the project. See [Projects](/guides/projects).

<Accordion title="How this works under the hood">
  Meridian signs a JSON Web Token with the private key and trades it with GitHub for an installation token. GitHub's installation tokens last one hour. Meridian keeps the token in memory and fetches a new one five minutes before the old one expires. It writes nothing to disk.
</Accordion>

## Polling

GitHub never calls Meridian. Meridian sees every push and workflow run within 30 seconds: every 30 seconds it reads each project's newest commit on its branch, and the branch's last 20 workflow runs.

Each request sends an ETag, the tag GitHub gave its last answer. When nothing changed, GitHub says so, and that costs none of your rate limit.

## GitHub Enterprise Server

Set `GITHUB_API_URL` to your server's API address:

```bash
GITHUB_API_URL=https://github.example.com/api/v3/
```

Create the App on your Enterprise server with the same settings. Links that Meridian shows, to repositories, commits and files, go to the same server. For the address above, that is `https://github.example.com`.

## Using a token instead

For a homelab or local development, a personal access token can stand in for the App. Set `GITHUB_TOKEN`, and leave `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` unset. Settings then shows **GitHub: Token**.

Meridian makes every call as the token's owner, and projects need no installation ID.

<Tabs>
  <Tab title="Fine-grained token">
    Give it access to the infra repository, with these repository permissions:

    | Permission | Access |
    | --- | --- |
    | Contents | Read and write |
    | Pull requests | Read and write |
    | Actions | Read and write |
    | Secrets | Read and write |
    | Workflows | Read and write |
    | Metadata | Read |
  </Tab>
  <Tab title="Classic token">
    Select the `repo` and `workflow` scopes.
  </Tab>
</Tabs>

<Warning>
  A token reaches every repository its owner can reach. An App reaches only the repositories you install it on. Use the App in production.
</Warning>

## What Meridian never does on GitHub

- It never reads secret values. GitHub's API lets you write Actions secrets but not read them. Meridian also encrypts each value with the repository's public key before it sends it.
- It never pushes to a branch other than the project's branch and its own `meridian/<slug>-<hex>` proposal branches.
- It never force-pushes. It writes one file at a time through GitHub's contents API.
- It never overwrites someone else's change. Each write to a file names the version of the file Meridian read, its blob SHA. If someone changed the file in the meantime, the write fails.
