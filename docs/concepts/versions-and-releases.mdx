Meridian keeps the version each app should run in a one-line file in Git. Deploys change that file, and its history is the app's releases.

## The idea

A [version](/reference/glossary#version) is the name of the build to run, such as `v42`. It is a Docker image tag. Kamal has no place for it in its config, so you pass it to `kamal deploy` as `--version`.

Meridian keeps it in a [version file](/reference/glossary#version-file) next to the app's config. Each commit that changes the file is a [release](/reference/glossary#release).

## The version file

The version file takes the config's name, with `.version` in place of `.yml`:

| Config | Destination | Version file |
| --- | --- | --- |
| `config/deploy.yml` | none | `config/deploy.version` |
| `config/deploy.yml` | `production` | `config/deploy.production.version` |
| `kamal/shop.yaml` | `staging` | `kamal/shop.staging.version` |

It holds one line, the image tag to run:

```text config/deploy.production.version
v42
```

A version starts with a letter, digit or `_`. Up to 127 more letters, digits, `_`, `.` or `-` follow. Meridian refuses anything else, because a leading `-` would read as a flag to Kamal.

The image must already be in your registry. The [CI workflow](/reference/glossary#ci-workflow) runs `kamal deploy --skip-push`, so it never builds one.

An app has no version file until its first deploy through Meridian, or until you commit one.

## Releases

A release's version is what the file held after its commit. The newest release is what Git says should run, and [drift](/concepts/drift) compares every server with it. Any commit to the file counts, whoever made it: a deploy from Meridian, a merged pull request, or a commit you push by hand.

Each release shows its version, the first line of its commit message, its author, its short commit ID and its age. The app's page shows the last 20.

### Without a version file

With no version file, each commit to the app's config is a release instead. For an app with a destination, it is each commit to the destination file. The release's version is the commit's short ID. Meridian can't compare that with an image tag, so the app shows as **unknown** on every server. The app's page says so under **Configuration**.

## Deploy, roll back and redeploy

All three act on the version file. They are on the app's page. [Deploy and roll back](/guides/deploy) has the steps.

- **Deploy** commits a new version to the file, on the default branch. Meridian refuses a version the file already holds, because a commit that changes nothing never starts the workflow.
- **Roll back** undoes the newest release with a new commit. The file gets back the value it held before. The button appears once an app has at least two releases. To go back further, deploy the older version.
- **Redeploy** runs the deploy workflow again for the version in the file now. It commits nothing. Use it after you rotate a secret, or when a deploy failed for a reason outside the image.

A deploy commit names the service and destination, then who pressed the button:

```text
deploy(shop-production): v42

Meridian-Actor: Ada Lovelace <ada@example.com>
```

<Note>
Deploys and rollbacks always commit straight to the default branch, even when the project opens pull requests for other changes. A branch rule that blocks direct pushes blocks them too, and Meridian shows GitHub's refusal.
</Note>

## Deploy status

A deploy's status comes from the runs of `.github/workflows/meridian-deploy.yml`, and no other workflow.

| Status | Meaning |
| --- | --- |
| `pending` | Meridian made the commit. No run has been seen yet. |
| `queued` | The run is waiting for a runner. |
| `in_progress` | Kamal is running. |
| `completed` | The run ended. Its result shows instead, such as **Success** or **Failure**. |

A version-file commit made outside Meridian gets a deploy too, credited to **Git**. Progress on each server comes from the agents. Under **Current deploy**, each server turns to **Running v42** when its agent reports that version.

<Accordion title="Edge cases">
  Meridian reads the 20 most recent commits to the version file at each sync where the file changed. It keeps every release it has seen. It orders releases by when each commit landed on the branch.

  A deploy sends GitHub the file's current Git SHA, its content ID. If someone changed the file since Meridian read it, GitHub refuses the write.

  Before a rollback, Meridian checks with GitHub that the release is still the newest commit to the file. If not, the rollback stops with a conflict, so a change Meridian hasn't seen is never undone. If the file didn't exist before that release, there is nothing to roll back to.

  Redeploy reads the version from GitHub when you press the button, not from the last sync.

  Meridian matches a workflow run to apps by its commit SHA. It checks for new runs every 30 seconds. Kamal deploys every host in one CI job, so CI can't report progress per server.
</Accordion>
